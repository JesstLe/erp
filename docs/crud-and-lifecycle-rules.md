# ERP 增删改查与业务生命周期规则

版本：V1 开发基线  
更新日期：2026-08-18

## 1. 结论

系统内每个可管理对象都必须提供与其业务性质相符的“增、查、改、删”能力，但“删”不等于一律物理删除：

- 服务项目、产品、设施、员工、顾客等主数据：支持新建、查询、编辑、停用/恢复。只有从未被任何业务引用的误建数据才允许物理删除。
- 消费单、支付、退款、会员资金流水、库存流水、接待与服务档案等业务事实：支持创建和查询；已生效记录不允许覆盖或物理删除，错误通过作废、反向单、退款、冲正或补充更正记录处理。
- 审计日志：只允许查询，不允许修改或删除。

这仍然是完整的业务管理能力。其目标是既让用户能纠错，又不破坏历史订单、库存、会员余额、财务报表和审计链。

## 2. 统一动作模型

| 用户意图 | 主数据 | 业务草稿 | 已生效业务记录 | 审计记录 |
|---|---|---|---|---|
| 增加 | 新建 | 新建草稿 | 由合法业务动作产生 | 系统自动产生 |
| 查询 | 列表、筛选、详情 | 列表、筛选、详情 | 列表、筛选、详情、下钻 | 多条件查询 |
| 修改 | 编辑允许变化的字段 | 可在提交前编辑 | 不覆盖原记录；使用更正、退款、冲正、反向单 | 不允许 |
| 删除 | 未被引用时物理删除；否则停用 | 无下游引用时可删除/取消 | 不允许物理删除；使用作废等状态动作 | 不允许 |
| 恢复 | 停用后恢复 | 取消前按状态机处理 | 仅允许业务定义的恢复动作 | 不适用 |

## 3. 查询能力统一要求

每个列表页不能只展示全量数据，至少应按对象提供以下查询条件：

- 关键词：编码、名称、单号、顾客姓名或脱敏手机号等适用字段。
- 状态：启用/停用，草稿/已确认/已结算/已作废等。
- 组织范围：租户、门店；普通账号只能查询授权范围。
- 时间范围：所有交易、流水、接待、服务记录和审计记录。
- 分页和稳定排序：数据量增长后不能一次加载全库。

查询由服务端执行租户隔离、权限过滤和参数校验；前端本地筛选不能替代服务端查询。

## 4. 修改与并发规则

- 所有更新请求携带 `expectedVersion`。数据库当前版本与页面版本不一致时返回 `VERSION_CONFLICT`，页面提示刷新后重试，禁止静默覆盖。
- 编码、业务单号、支付渠道流水号等稳定标识创建后不可修改。
- 历史订单保存项目名称、单位、价格等快照；修改主数据不能倒改历史单据。
- 每次新建、编辑、停用、恢复、删除、作废、退款和冲正都记录操作者、门店、对象、前后值、时间和追踪号。
- 前端隐藏按钮只用于改善体验；后端必须再次验证角色、租户、门店范围、状态和版本。

## 5. 删除判定规则

### 5.1 服务项目

物理删除前检查：价格版本行、接待预计项目、消费单项目行。任一存在即返回 `RESOURCE_IN_USE`，用户只能停用。

### 5.2 产品

物理删除前检查：产品图片、价格版本行、消费单产品行、库存余额、库存预留、库存流水、库存单据行和退货记录。任一存在即返回 `RESOURCE_IN_USE`，用户只能停用。

产品一旦产生订单或库存记录，`trackInventory` 库存跟踪属性被锁定；名称、单位和启停状态仍可按权限维护。

### 5.3 其他对象

- 顾客：有接待、会员、余额、订单或服务档案时不得删除；使用停用、合并或资料更正。
- 员工/账号：有排班、操作日志或业绩归属时不得删除；员工离职与登录账号停用分别处理。
- 设施：有使用历史时不得删除；使用停用。设施分组或类型删除前必须确认没有设施引用。
- 价格版本：仅未发布草稿可删除；已发布版本永久保留。
- 支付方式/支付渠道：有历史分摊或渠道订单后不得删除；使用停用。

## 6. 当前实现覆盖与缺口

状态定义：`已实现`表示当前前后端已有完整入口与保护；`部分实现`表示已有部分动作；`按生命周期管理`表示故意不提供物理修改或删除。

| 模块 | 增加 | 查询 | 修改 | 删除/替代动作 | 当前状态与下一步 |
|---|---|---|---|---|---|
| 服务项目 | 是 | 关键词、状态 | 名称、标准时长、状态 | 未引用可删；否则停用/恢复 | 已实现 |
| 产品目录 | 是 | 关键词、状态 | 名称、单位、库存属性、状态、图片 | 未引用且无图片可删；否则停用/恢复 | 已实现 |
| 设施配置 | 是 | 按门店查看 | 服务区、服务位及可选信息 | 停用语义 | 已具备主要能力；继续补物理删除判定和筛选 |
| 顾客档案 | 是 | 姓名/手机号/卡号及详情 | 基本资料编辑待补 | 停用、合并待补 | 部分实现，列为下一开发切片 |
| 员工与账号 | 是 | 列表 | 账号启停已具备，资料编辑待补 | 离职/账号停用，禁止删历史 | 部分实现，列为下一开发切片 |
| 价格版本 | 是 | 列表与明细 | 发布后不可改；草稿编辑待补 | 草稿删除/取消待补 | 部分实现 |
| 会员卡与储值 | 是 | 顾客详情内查询 | 通过状态动作和更正流程 | 退款/冲正，不物理删除 | 按生命周期管理；补充检索列表 |
| 接待与设施占用 | 是 | 看板、待录单队列 | 通过开始/暂停/继续/结束命令 | 异常取消需原因与审计 | 按生命周期管理 |
| 消费单与支付 | 是 | 收银及订单查询 | 草稿可改；确认后锁定 | 作废、退款、渠道关闭 | 按生命周期管理；继续增强组合查询 |
| 库存 | 单据产生 | 余额、流水、单据查询 | 不改已过账流水 | 反向调整单、退货 | 按生命周期管理 |
| 服务档案 | 是 | 顾客详情内查询 | 追加更正说明待补 | 不删除；隐私处置走独立流程 | 部分实现 |
| 审计日志 | 系统产生 | 多条件查询 | 否 | 否 | 已按不可变记录设计 |

## 7. 页面交互规范

- 列表页固定提供查询区、结果表格、分页、状态标识和行级操作区。
- “删除”必须二次确认，并明确“仅未被业务引用的数据可删除”。
- 被引用时不显示含糊的“操作失败”，应提示“已有业务记录，请停用而不是删除”。
- 停用后默认不出现在新订单、新接待和新价格配置的可选项中，但历史详情仍显示原名称或快照。
- 编辑弹窗明确必填和选填字段；不可变编码置灰并说明原因。
- 操作成功后刷新所有相关查询；版本冲突后要求刷新，不自动重试写请求。

## 8. 验收用例

1. 最高权限账号可按编码/名称和状态查询服务项目、产品。
2. 编辑后列表显示新值，编码保持不变，版本递增，审计日志可查到前后值。
3. 两个页面同时编辑同一对象，后提交的旧版本请求被拒绝且不覆盖先提交结果。
4. 未进入任何业务的服务项目/产品可经二次确认永久删除。
5. 已进入价格、接待、订单或库存的对象删除失败，并明确引导停用。
6. 停用对象不影响历史订单和报表，恢复后可重新用于新业务。
7. 非最高权限账号即使手工调用写接口也返回无权限。
8. 已结算支付、会员资金流水、库存流水和审计日志不存在物理删除入口。
