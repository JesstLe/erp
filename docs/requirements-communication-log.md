## 第一轮：子页面CRUD和字段规则

### 用户提出的问题

一些子页面包含新增、查询、修改、删除等操作，需要明确不同字段是否有必填、选填或其他限制。

### 讨论结论

字段不能只分“必填”和“选填”，至少需要以下六类：

| 类型 | 含义 | 示例 |
|---|---|---|
| 必填 | 不填写不能提交当前业务动作 | 所属门店、业务日期、退款原因 |
| 条件必填 | 满足条件时必须填写 | 选择外部支付后填写交易参考号 |
| 选填 | 不影响业务成立 | 备注、手工票号 |
| 系统生成 | 系统产生，用户不能编辑 | 系统单号、创建时间、操作人 |
| 自动计算 | 由其他字段计算 | 应收金额、优惠合计、余额 |
| 只读/状态锁定 | 特定状态后不能修改 | 已结算金额、已审核业务日期 |

同一个字段在不同动作和状态下可以有不同规则。

### 新增规则

- 新增时必须填写使业务能够成立的最小字段集合。
- 散客接待允许顾客身份选填；会员开卡时姓名、手机号和卡类属于业务必填。
- 开始设施使用时门店、设施和开始动作必填，开始时间由系统生成。
- 消费结算时至少存在一条有效项目/产品明细，实际金额和支付处理方式必填。
- 采购订单需要供应商、收货门店、商品、数量和价格。

### 查询规则

- 查询条件通常选填，但必须受数据权限和最大范围限制。
- 日期范围提供安全默认值，例如最近7天或30天。
- 门店范围根据当前用户权限自动限制。
- 手机号、会员卡号、单号和摘要可以作为可选精确查询条件。
- 无条件查询不得让普通用户读取全部门店和全部历史数据。
- 大范围查询应要求补充日期、门店或业务类型，并转为受控异步任务。

### 修改规则

- 草稿状态允许修改业务字段。
- 已提交后，普通人员不能修改金额、数量、对象等关键字段。
- 已审核、已结算、已过账或已出入库记录不能直接修改。
- 已生效记录发生错误时，通过撤回、作废、退款、冲正或调整单处理。
- 系统单号、创建人、原始流水号、支付请求号和原单关系永远不能人工修改。
- 并发编辑使用版本号校验，禁止后保存的人静默覆盖先保存结果。

### 删除与作废规则

- 未提交且未产生业务影响的草稿可以删除。
- 已提交未审核单据根据权限执行撤回或作废。
- 已支付、已出入库、已扣会员权益或已计提工资的记录禁止物理删除。
- 作废原因属于必填字段，并记录操作者、时间、审批和影响范围。
- 已产生资金、库存或权益影响时，必须使用退款、退货、冲正或补偿流水。

### 表单示例

| 页面 | 必填 | 条件必填 | 选填/系统字段 |
|---|---|---|---|
| 开始设施使用 | 门店、设施、开始动作 | 预约到店时关联预约 | 顾客可选；开始时间系统生成 |
| 消费结算 | 消费明细、实际金额、支付方式 | 改价原因、外部交易参考号 | 备注、顾客身份（散客时） |
| 顾客储值 | 会员、储值金额、支付方式 | 奖励规则、人工支付凭证 | 顾问、摘要 |
| 消费退款 | 原消费单、退款明细、金额、原因 | 非原路退款原因及审批 | 备注、附件 |
| 采购订单 | 供应商、门店、商品、数量、价格 | 规则启用时填写交货日期 | 手工单号、备注 |
| 采购入库 | 供应商、仓库、商品、实收数量 | 批次商品的批次和效期 | 手工票号、备注 |

### 后续文档产物

每个核心表单建立字段级需求矩阵，至少包含：

```text
字段名称
业务含义
数据类型
必填类型
条件必填表达式
默认值
数据来源
新增时是否可编辑

```

### 证据边界

参考系统只进行了只读页面查看，没有保存或提交表单。因此可以确认页面字段存在，但不能把参考系统实际后端必填校验写成已经验证；新系统字段规则由业务逻辑和验收用例共同确定。

## 第二轮：代码版本更新、热更新与一键发布

### 用户提出的问题

开发完成后如果修改代码，系统应该如何更新；是否采用热更新，能否一键更新，以及用什么成熟工具管理版本替换。

### 讨论结论

- 不采用运行中的后端程序直接覆盖文件的传统热更新。
- 正式更新采用“Git版本管理 + 自动构建 + 不可修改版本包 + 发布审批 + 备用实例部署 + 健康检查 + 流量切换”。
- 单台Windows服务器使用IIS双版本/双站点切换，形成单机A/B发布。
- 数据库先执行向后兼容迁移，程序回退时数据库通常不自动降级。
- 功能开关用于控制功能是否开放，但不替代代码发布和数据库迁移。
- 一键发布入口位于独立部署平台，不放在ERP业务系统内部。

### 推荐发布链路

```mermaid
flowchart LR
    A["修改代码并提交Git"] --> B["自动测试和安全检查"]
    B --> C["生成带版本号和校验值的发布包"]
    C --> D["部署测试环境并验收"]
    D --> E["批准生产发布"]
    E --> F["发布前检查与数据库备份"]
    F --> G["Flyway向后兼容迁移"]
    G --> H["部署备用应用实例"]
    H --> I["健康检查与冒烟测试"]
    I --> J["IIS切换流量"]
    J --> K["观察并记录发布结果"]
```

### 单服务器A/B更新

```text
D:\erp\sites\blue
D:\erp\sites\green
D:\erp\releases\1.0.0
D:\erp\releases\1.0.1
```

更新过程：

1. 当前Blue对外提供服务。
2. 新版本部署到Green，暂不接收正式流量。
3. Green执行健康检查、数据库兼容检查和关键业务冒烟测试。
4. 全部通过后由IIS将流量切换至Green。
5. Blue停止运行但保留版本文件。
6. 新版本异常时将流量切回Blue。

该方案可以降低普通代码发布中断，但单服务器本身仍是单点，Windows重启和服务器故障无法做到零停机。

### 可即时生效与不可热更内容

可以通过配置或功能开关即时生效：

- 促销活动启停。
- 支付方式启停。
- 门店参数。
- 已发布价格版本按生效时间切换。
- 权限配置。
- 功能开关。
- 前端静态资源按版本更新缓存。

不得通过普通热更新替换：

- 后端资金和库存事务代码。
- 会员余额扣减逻辑。
- 支付、退款和对账代码。
- 认证和权限核心逻辑。
- 数据库表结构。

### 工具方案

| 层次 | 推荐成熟方案 | 预算优先备选 |
|---|---|---|
| 代码仓库 | GitHub私有仓库 | GitLab或其他受控Git仓库 |
| 自动构建 | GitHub Actions | 对应仓库CI或自建CI |
| Windows发布 | Octopus Deploy + Windows Tentacle | 受控PowerShell发布脚本 |
| Web切换 | IIS A/B站点或应用实例 | IIS版本目录切换和应用池重启 |
| 数据库迁移 | Flyway版本化SQL | 不允许退化为手工改表 |

正式工具组合仍需结合预算、代码仓库和后端技术栈确定。Octopus是推荐项，不在本轮自动视为已经采购。

### 版本包

```text
erp-server-1.0.1.zip
erp-web-1.0.1.zip
database-migrations-1.0.1.zip
release-manifest-1.0.1.json
```

发布清单至少包含：

- 版本号和Git提交号。
- 构建时间和文件SHA-256校验值。
- 支持的最低/最高数据库schema版本。
- 包含的数据库迁移。
- 配置版本和功能开关要求。
- 版本说明、已知风险和程序回退方式。

版本号建议：

- `1.0.0`：第一版正式发布。
- `1.0.1`：兼容性错误修复。
- `1.1.0`：向后兼容的新功能。
- `2.0.0`：重大不兼容版本。

### 发布失败处理

| 失败阶段 | 处理方式 |
|---|---|
| 自动测试失败 | 不生成正式版本 |
| 测试部署失败 | 禁止进入生产 |
| 数据库校验失败 | 停止发布，不执行后续步骤 |
| 备用实例健康检查失败 | 废弃失败实例，正式流量不切换 |
| 流量切换后应用异常 | 切回上一应用版本 |
| 新版本写入错误数据 | 关闭功能、执行补偿迁移或冲正 |
| 严重数据损坏 | 恢复到隔离数据库核对后再处理生产 |

### 当前待确认

- 代码仓库最终采用GitHub、GitLab还是其他平台。
- 是否采购/使用Octopus Deploy，或第一阶段采用PowerShell发布流程。
- 后端技术栈确定后，IIS具体承载方式和应用服务形式。
- 对外营业时允许的最大发布中断时间。

## 2026-08-22：库存数量入口与自动业务编码

### 库存数量如何修改

- 产品目录只维护名称、单位、图片和是否跟踪库存，不允许直接覆盖库存余额。
- 商品库存页为有权限账号提供右上角“调整库存”和每个商品行内的“调整数量”。
- 用户选择期初、收货入库、盘盈或盘亏，填写正整数变动数量和原因；增减方向由单据类型决定。
- 已过账流水不能修改或删除，录错必须新增反向调整；销售结算出库和商品退货入库继续由原业务流程自动生成。

### 系统主键与业务编码分离

- 数据库内部关系使用不可见 UUID 主键；页面显示的编码是稳定业务标识，不是数据库主键。
- 新建品牌、门店、服务、产品、员工、会员卡类、供应商和服务位时，系统编码统一由后端事务升序生成，前端不提供自定义系统编码输入框。
- 当前格式为品牌 `B+日期+四位流水`、门店 `S001`、服务 `SV000001`、产品 `PD000001`、员工 `EMP000001`、卡类 `CT000001`、供应商 `SUP000001`、门店服务位 `F0001`。
- 编码一经分配永久不变；名称可以修改；停用或删除后编号不回收复用，允许出现跳号。
- 生成器使用数据库 `(sequence_name, scope_key)` 原子递增和业务表唯一索引双重保护；客户端即使额外提交 `code` 字段也不能指定系统编码。
- 旧系统原编号通过迁移来源实体、来源主键和来源哈希映射保留，不占用或覆盖新系统自动编号。

## 2026-08-22：正常交班自动关班

- 产品反馈：小型门店可能只有店长兼任收银员，如果所有交班都要求另一人复核，正常班次会长期卡在待复核。
- 已确认规则：店长仍可复核授权门店中其他员工的异常班次；任何人都不能复核自己提交的异常班次。
- 提交交班时，若实际现金等于理论现金且人工微信/支付宝待核对金额为0，系统直接自动关班，不再生成无意义的人工复核任务。
- 只要存在现金差额或人工外部待核对，班次仍进入待复核；10元以内现金差额可由另一名店长或OWNER处理，超过10元或存在外部待核对必须由另一名OWNER处理。
- 消费单结算和收入入账与交班复核分离：已经收款的订单不会因为班次待复核重新显示为待支付。

## 2026-08-22：OWNER必须能够兜底完成交班闭环

- 用户确认：OWNER是品牌内最高权限和最终业务兜底角色，必须能够把交班复核等业务流程完整跑通，不能因本人同时是开班或交班操作者而永久卡在待复核。
- 本规则覆盖上一节“任何人都不能复核自己异常班次”的限制：普通店长和收银角色仍禁止自我复核，OWNER允许复核本人班次。
- 现金差额超过10元或存在人工外部待核对时仍只允许OWNER处置；OWNER本人复核时差额或待核对说明必填，复核人、原操作者、金额快照和状态变化继续完整进入审计。
- 前端不得把OWNER的本人班次复核按钮置灰，后端必须按服务端角色再次授权，不能仅依赖页面放行。

## 价格版本 CRUD 规则

- 价格版本页面提供新增、名称自动查询、状态/生效日期筛选、详情查看、草稿修改、复制、停用和删除。
- 已发布版本不直接修改；需要改价时复制为新草稿再编辑。
- `OWNER` 可以删除草稿、已发布或已停用版本，删除必须填写原因并进入审计。
- 删除已被消费单引用的价格版本时，只解除消费单的版本引用；订单行已经保存的项目名称、标准价、成交价和金额继续保留，消费单、支付、退款和报表数据不随价格版本删除。
