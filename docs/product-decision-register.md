更新日期：2026-08-18

## 状态定义

- `已采用`：已经进入当前设计基线，后续变更需要新决策替代。
- `待确认`：尚不能作为最终开发或采购依据。
- `已替代`：被后续决策替代但保留追溯。

## CRUD与字段规则

| 编号 | 状态 | 决策 |
|---|---|---|
| CRUD-001 | 已采用 | 字段分为必填、条件必填、选填、系统生成、自动计算和只读/状态锁定 |
| CRUD-002 | 已采用 | 同一字段在新增、修改、查询、审核和作废动作下可以有不同规则 |
| CRUD-003 | 已采用 | 草稿允许修改；已审核、已结算或已过账记录禁止直接修改 |
| CRUD-004 | 已采用 | 已产生资金、库存、会员权益或工资影响的记录禁止物理删除 |
| CRUD-005 | 已采用 | 已生效记录通过撤回、作废、退款、冲正或调整单修复 |
| CRUD-006 | 已采用 | 查询条件可选但必须受日期、门店、权限和最大数据范围限制 |
| CRUD-007 | 已采用 | 每个核心表单必须建立字段级需求矩阵并映射到接口和数据库字段 |
| CRUD-008 | 已采用 | 参考系统未提交表单，因此其后端必填校验不能标记为已验证 |
| CRUD-009 | 已采用 | 所有可管理对象必须提供与业务性质相符的新增、查询、修改和删除或替代动作，不能只实现新增 |
| CRUD-010 | 已采用 | 主数据未被引用时可物理删除，已引用后只能停用或恢复；已生效业务事实通过作废、退款、冲正、反向单或补充更正处理 |
| CRUD-011 | 已采用 | 所有主数据修改携带预期版本并记录前后值；稳定编码创建后不可修改；删除前由服务端检查全部业务引用 |

## 变更规则

- 新决策使用新编号，不修改旧编号含义。
- 决策变化时将原决策标记为“已替代”，并写明替代编号。
- `待确认`项目不能作为采购、不可逆数据库设计或正式验收的唯一依据。
- CRUD决策变化时同步字段矩阵、接口校验、数据库约束和测试用例。
- 发布决策变化时同步部署基线、数据库治理、发布脚本和恢复演练。

## V1权限与审批阈值

| 编号 | 状态 | 决策 |
|---|---|---|
| AUTH-001 | 已采用 | V1采用角色、门店范围、字段、状态和金额阈值组合授权，前端可见性不替代服务端鉴权 |
| AUTH-002 | 已采用 | 前台默认可执行正常开始、暂停、继续、换设施和结束服务，但不能改价、支付或退款 |
| AUTH-003 | 已采用 | 店长改价必须填写原因；同时满足单行降幅不超过10%且整单差额不超过50元时可自批，任一超限由最高权限账号审批 |
| AUTH-004 | 已采用 | 前台和收银员的默认改价阈值为0；收银员只能按标准价或已审批价格结算 |
| AUTH-005 | 已采用 | 单笔储值本金加奖励金扣减达到500元时要求完整手机号核对和一次性验证码 |
| AUTH-006 | 已采用 | 现金交班差额绝对值不超过10元可由未参与该班次交班的店长复核；更大现金差额或任何外部渠道差异由最高权限账号处理 |
| AUTH-007 | 已采用 | V1所有已结算退款均从原单发起并由最高权限账号批准；无法原路退款进入异常退款流程 |
| AUTH-008 | 已采用 | 权限和阈值均为版本化配置，本文数值仅为空库初始化值，禁止写死在业务代码中 |
| AUTH-009 | 已采用 | 会员储值本金与赠送奖励必须分账；同卡消费强制先扣本金、本金耗尽后才能扣奖励；消费退款按原扣款分摊退回原账户，储值整单冲正必须同时收回全部本金与奖励，奖励不得折现或单独退款 |
| AUTH-010 | 已采用 | 微信/支付宝日账单只能由最高权限账号执行和登记差异处置，店长只读；差异处置必须填写原因且只推进对账状态，不得直接修改原支付、退款、消费单或会员余额 |
| AUTH-011 | 已采用 | 商品消费单确认时只预占库存、可信结算时才销售出库、作废释放预占；商品退货只确认实物回库且由最高权限执行，资金退款必须另走原支付审批，两者不得互相隐式触发 |
| AUTH-012 | 已采用 | 服务与商品不强制绑定；消费单可仅服务、仅商品或混合。新价格版本允许只提交本次服务或商品调价，未提交的已有价格继承为完整快照，从未定价的条目保持不可销售且不阻塞其他条目发布 |
| AUTH-013 | 已采用 | 产品封面图选填且不参与定价库存；服务档案除系统时间与归属字段外均选填，可选关联消费单但不复制金额。服务档案及图片仅OWNER和STORE_MANAGER可见，文件加密存储，档案与附件关系不可更新或删除 |
| AUTH-014 | 已采用 | 设施配置从日常接待中独立：OWNER可查看全部租户门店、店长和设施配置并跨店维护，STORE_MANAGER只维护授权门店。服务名称、内部设施名称和参考单价均选填；参考单价不得自动进入收银，历史服务位只停用不物理删除 |
| AUTH-015 | 已采用 | 设施接待可选关联当前门店顾客和租户内已启用预计服务；设施看板与待录单展示顾客原名，不展示手机号。预计服务是识别提示，必须由操作人明确带入并核对后才能成为消费单草稿明细 |
| AUTH-019 | 已采用 | 顾客姓名在授权业务页面按原名展示；手机号列表和详情仅隐藏中间四位，格式为前三位加四个星号加后四位。输入完整手机号时使用服务端HMAC检索哈希精确定位，接口仍只返回掩码号码 |
| AUTH-016 | 已采用 | 服务明细选择当前门店有效员工；提成规则只由OWNER在服务项目维护，支持成交金额比例或每次固定金额，收银和店长只能选择员工不能临时改提成 |
| AUTH-017 | 已采用 | 员工、规则、基数和提成毛额写入订单明细快照；提成不得超过服务成交金额；普通收银员不得读取提成参数或员工提成报表 |
| AUTH-018 | 已采用 | V1整单退款按退款占应收比例冲减各服务行提成，报表分开展示毛额、退款冲减和净额；动态经营报表不等于工资已发放 |

## V1状态机与完成语义

| 编号 | 状态 | 决策 |
|---|---|---|
| STATE-001 | 已采用 | 设施使用、接待、消费单、支付、渠道核对、会员账户和收银班次分别建模，不合并为一个状态字段 |
| STATE-002 | 已采用 | 打开、查看、搜索和刷新严格只读；占用设施、创建接待和创建账单只能由显式命令触发 |
| STATE-003 | 已采用 | 设施计时以服务端时间为准且不参与自动计价；结束设施使用可释放设施，但不等于消费单已经结算 |
| STATE-004 | 已采用 | 所有写命令使用全局幂等键和聚合版本号；设施占用、会员余额和退款累计还必须由数据库约束防并发超用 |
| STATE-005 | 已采用 | 支付结果、支付来源确认和财务对账使用独立状态轴；人工登记微信或支付宝只能标记待核对，不能伪装为渠道确认 |
| STATE-006 | 已采用 | 外部渠道成功但内部入账不完整时进入REVERSAL_REQUIRED并禁止重复普通结算，不回退成未支付状态 |
| STATE-007 | 已采用 | 已结算单据和账户流水不可原地修改或物理删除；退款、冲正和调整均新增关联的反向流水 |
| STATE-008 | 已采用 | 首个闭环以V1核心状态机与验收用例中的P0案例为工程完成基线；状态变更必须同步契约、数据库约束和自动化测试 |
| STATE-009 | 已采用 | 待录单队列以顾客、预计服务、设施和到店时间作为主要识别信息，机器接待单号仅作次要追溯；占用时长自适应显示到秒但不参与计价；关联上下文不会自动创建消费单、确认金额或触发收款 |
