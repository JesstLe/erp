# ERP 核心功能业务逻辑总览

版本：v2

日期：2026-08-18

依据：参考系统只读遍历、收银资金链核对和已确认的门店实际场景。

## 1. 产品业务骨架

系统以五类不可混淆的事实为核心：

1. **现场事实**：顾客到店、设施占用、服务开始与结束。
2. **业务单据事实**：消费、储值、采购、销售、配货、退款等业务内容和责任人。
3. **台账事实**：会员权益、库存、应收应付和员工业绩的逐笔变动。
4. **资金事实**：收款、付款、退款、支付渠道、手续费和对账状态。
5. **分析事实**：由已生效业务与台账按统一指标版本计算的报表和决策数据。

查看页面不能创造任何上述事实；保存草稿也不能隐式改变库存、余额、资金或设施状态。

## 3. 四条核心端到端链路

### 3.1 门店服务、结算与交班

到店/预约 → 接待 → 明确占用设施 → 服务 → 结束并释放设施 → 店长录入服务、商品和金额 → 关联会员/散客 → 优惠与权益核验 → 消费单确认时预占商品 → 组合支付 → 可信结算时商品出库 → 交班对账。

关键边界：设施计时不自动收费；老板维护标准价，店长只确认本次实际价；微信与支付宝交易及原路退款代码已具备，但在真实商户验收并按门店启用前仍使用人工登记待核对。详细设计见 [微信支付与支付宝支付开发设计](payment-integration-development-guide.md)。

### 3.2 会员资金与权益

顾客唯一识别 → 开卡 → 储值/奖励/购次卡/积分 → 消费扣减 → 退款/退卡/调整 → 欠款还款 → 余额与负债分析。

关键边界：本金、奖励、积分、次卡和欠款分别建账；余额只能由流水驱动；退款按原业务版本冲回。

### 3.3 商品供应链

采购需求 → 采购订单 → 到货验收 → 入库及应付 → 配货申请 → 仓库出库 → 在途 → 门店收货 → 销售/消费出库 → 退货/盘点/调价。

关键边界：订单不改账面库存；出入库才写库存流水；在途不等于门店现货；应付/应收与实际收付款分开。

### 3.4 经营管理

业务事件 → 会员/库存/资金/业绩台账 → 统一指标模型 → 报表 → 目标和阈值比较 → 异常待办 → 业务模块处理 → 复核关闭。

关键边界：报表和驾驶舱只读；所有数字可下钻到只读原单；不同模块不能各算一套营业额、毛利或会员负债。

## 4. 全局状态与动作原则

- 查看：零业务写入。
- 草稿：允许编辑，但不改变余额、库存、资金或已发布配置。
- 提交/审核：确认业务意图与权限，不等于已经执行资金或库存动作。
- 执行：使用幂等请求写入台账或调用外部渠道。
- 核对：确认系统记录与现金、渠道、银行或实物事实一致。
- 退款/冲正：引用原业务反向记录，不覆盖或物理删除历史。
- 关班/关账：锁定已核对期间；后续修复使用调整或冲正。

## 5. 已确认的产品决策

- 设施占用和计时只记录现场信息，与收费金额不关联。
- 顾客身份可以在服务开始后补录，结算前完成会员关联。
- 标准价格由最高权限账号确定并版本化。
- 服务项目与产品互不强制绑定；消费单允许仅服务、仅商品或混合明细。新价格版本只要求填写本次变更项，其他已有生效价格继承为完整只读快照，从未定价的条目不能销售。
- 店长录入或确认本次服务内容、时长和实际成交金额；发生改价必须填写原因，超过可配置金额或比例阈值时由最高权限复核。
- 第一期服务单一品牌下的多门店，业务表保留租户字段但不开放多商户管理后台。
- 新系统从空库开始，不迁移旧系统会员、余额、订单和历史流水。
- 一个设施同一时刻只允许一条有效使用记录；一次接待可以按顺序或并行关联多个设施，结束后支持待清洁状态。
- 会员可按姓名和手机号辅助查询；真正扣减权益时校验完整手机号，大额扣减按可配置阈值增加验证码确认。
- 微信 Native 与支付宝订单码已形成交易及原路退款代码；未完成商户接入验收前继续支持人工登记待核对。
- 商品消费确认只预占库存，结算才出库，作废释放预占；商品退货回库与资金退款分别执行、分别审计。
- 已生效财务、库存、会员权益和工资记录不能物理删除。
- 参考模板中的股权、微信运营/营销和云商模块不纳入当前版本范围；收银所需的微信支付通道独立设计。

## 6. 仍需业务确认

- 店长改价和会员大额扣费的初始金额/比例阈值。
- 微信/支付宝采用普通商户直连、服务商代接还是其他商户模式，以及门店是否共用商户号。
- 批次、效期、序列号、多单位和成本算法的第一期范围。
- 次卡、储值和服务跨门店使用时的内部结算规则。
- 收银交班差额、退款原路限制和无法原路退款的授权规则。
- 排班考勤、专业会计总账和发票是否纳入第一期。
