# ERP V1 角色权限与审批阈值矩阵 v1

日期：2026-08-18  
状态：已采用，作为 V1 服务端鉴权、前端交互、审批和测试基线  
关联页面：[V1页面清单与字段级需求矩阵](v1-page-and-field-matrix.md)

## 1. 权限设计原则

V1采用“角色默认权限 + 门店数据范围 + 字段权限 + 金额阈值 + 当前业务状态”的组合授权，不使用单一角色名称直接决定全部能力。

- 页面可见不等于动作可执行；每个写操作由服务端重新鉴权。
- 同一个员工可以兼任多个角色，最终权限取有效授权并集，但显式禁止项和职责分离规则优先。
- 最高权限账号拥有最终定价和高风险审批权，但不能跳过原因、幂等、状态校验和审计。
- 店长默认只管理被授权门店；不能看到或操作其他门店业务。
- 前台负责接待现场，收银员负责资金结算，两者默认不自动互相继承权限。
- 技师不是 V1 核心管理角色；默认只能查看本人被分配的服务任务，不具备设施状态、改价、支付和退款权限。
- 所有阈值存入版本化配置，代码中不得写死。本文数值是空库初始化的推荐值，可由最高权限账号发布新版本调整。

## 2. 标准角色

| 代码 | 角色 | 默认数据范围 | 核心职责 | 默认禁止事项 |
|---|---|---|---|---|
| `OWNER` | 最高权限/老板 | 全品牌、全部门店 | 组织初始化、价格发布、权限、支付配置、高风险审批、全局审计 | 仍不得直接改已结算流水、删除审计或绕过状态机 |
| `STORE_MANAGER` | 店长 | 指定门店 | 现场经营、设施接待、服务录单、授权范围内改价、交班复核 | 不发布价格档案、不修改角色模型、不确认外部渠道“已成功” |
| `FRONT_DESK` | 前台 | 指定门店 | 顾客接待、设施操作、顾客查询与快速建档 | 不改价、不扣会员资金、不确认支付、不退款 |
| `CASHIER` | 收银员 | 指定门店、本人班次 | 录单检查、会员权益核销、组合支付、开班交班 | 不维护标准价格、不审批自己的超限改价、不复核自己的交班差额 |
| `TECHNICIAN` | 技师/服务员工 | 指定门店、本人任务 | 查看本人任务、填写服务建议或实际服务时长草稿 | 不改变设施状态、不关联会员权益、不改金额、不收款 |

后续可增加财务、审计、顾客运营和目录管理员等专用角色，但不能通过扩大上述门店角色默认权限替代职责分离。

## 5. 消费单、价格与审批权限

### 5.1 默认动作

| 权限代码 | 动作 | OWNER | STORE_MANAGER | FRONT_DESK | CASHIER | 规则 |
|---|---|---:|---:|---:|---:|---|
| `order.draft.create` | 创建消费单草稿 | ✓ | ✓ | ✓ | ✓ | 不产生资金或权益影响 |
| `order.line.use_standard_price` | 按生效标准价录明细 | ✓ | ✓ | ✓ | ✓ | 价格由后端读取并保存版本快照 |
| `order.price.override` | 修改本次实际成交价 | ✓ | 阈值内 | — | — | 店长任何改价都必须填写原因 |
| `order.price.override.approve` | 审批超阈值改价 | ✓ | — | — | — | 申请人与审批人不能是同一普通角色 |
| `order.submit_checkout` | 提交待结算 | ✓ | ✓ | — | ✓ | 超限改价必须先批准 |
| `payment.collect` | 执行现金/会员/组合支付 | ✓ | ✓ | — | ✓ | 必须有开放班次或具备代收权限 |
| `payment.manual_external_record` | 登记外部人工收款 | ✓ | ✓ | — | ✓ | 只能进入“人工登记待核对” |
| `payment.channel_verify` | 将外部支付标记为渠道确认 | 系统 | 系统 | — | 系统 | 仅合法回调或主动查单；人不能点击成功 |
| `order.void_unpaid` | 作废未支付已提交单 | ✓ | ✓ | — | 发起 | 原因必填；不存在资金/权益影响 |
| `order.refund.initiate` | 从原单发起退款 | ✓ | ✓ | — | 发起 | 不允许自由录入无来源退款 |
| `order.refund.approve` | 批准退款 | ✓ | — | — | — | V1所有已结算退款均由OWNER批准 |

### 5.2 改价推荐初始阈值

空库初始化以下配置：

| 配置项 | 推荐值 | 判断方式 | 超限处理 |
|---|---:|---|---|
| 店长单行降价比例上限 | `10%` | `(参考单价-实际单价)/参考单价` | 提交OWNER审批 |
| 店长整单降价金额上限 | `¥50.00` | `参考总额-实际总额` | 提交OWNER审批 |
| 手工高于标准价 | `不允许店长直接执行` | 实际单价高于参考单价 | 优先添加真实增项；确需手工加价时提交OWNER审批 |
| 前台/收银员改价上限 | `¥0.00 / 0%` | 任意价格偏差 | 无权改价，只能退回店长处理 |

店长自批必须同时满足“单行降幅不超过10%”和“整单差额不超过50元”。只要任一条件超限，就必须在结算前完成OWNER审批。阈值按价格配置版本保存，历史订单记录当时阈值版本。

改价原因使用可配置原因码并允许补充说明。推荐原因码：`服务内容调整`、`顾客投诉补偿`、`活动补录`、`抹零`、`其他（必须说明）`。

## 6. 会员权益与顾客敏感信息权限

### 6.1 会员权益动作

| 动作 | OWNER | STORE_MANAGER | FRONT_DESK | CASHIER | 初始规则 |
|---|---:|---:|---:|---:|---|
| 查询权益摘要 | ✓ | ✓ | 接待所需摘要 | 结算所需摘要 | 默认脱敏卡号，只显示可用余额/次数 |
| 储值/奖励扣减 | ✓ | ✓ | — | ✓ | 只能通过支付分摊和不可变流水 |
| 次卡核销 | ✓ | ✓ | — | ✓ | 必须匹配项目、有效期和门店范围 |
| 顾客储值 | ✓ | ✓ | — | ✓ | 先形成储值单，支付后入账 |
| 人工调余额/次数 | — | — | — | — | V1不提供直接修改；只能冲正或专项调整单 |

### 6.2 大额权益扣减验证

推荐初始阈值：单笔使用“储值本金 + 奖励金”的合计达到 `¥500.00` 时，除员工权限与完整手机号核对外，还必须通过发送到会员已验证手机号的一次性验证码。

- 阈值以下：核对完整手机号后可继续。
- 阈值以上或等于阈值：核对完整手机号 + 一次性验证码。
- 无法接收验证码：不能由收银员跳过；由店长发起异常申请，OWNER批准后使用受审计的替代验证流程。
- 验证码只保存哈希、用途、有效期、尝试次数和结果，不保存明文。

## 7. 开班、交班、差额与复核

| 权限代码 | 动作 | OWNER | STORE_MANAGER | CASHIER | 规则 |
|---|---|---:|---:|---:|---|
| `shift.open` | 开班 | ✓ | 代开并说明 | ✓本人 | 同门店同收银员仅一条开放班次 |
| `shift.handover.submit` | 提交交班 | ✓ | 代办并说明 | ✓本人 | 各渠道实交必填；差额非0原因必填 |
| `shift.review.cash_small` | 复核小额现金差额 | ✓ | ✓ | — | 只限绝对值不超过 `¥10.00` 的现金差额 |
| `shift.review.high_risk` | 复核高风险差额 | ✓ | 发起/说明 | — | 现金差额超过10元或任何外部渠道差异 |
| `shift.close` | 完成关班 | ✓ | 无高风险差额时✓ | — | 高风险差额必须先经OWNER结论 |

推荐关班时限：交班提交后 `24小时` 内完成复核；超过时限形成OWNER待办，不自动篡改或关闭班次。

收银员不能复核自己的差额；店长若代收银或提交了该班次交班，则不能作为该班次唯一复核人，需OWNER处理。

## 8. 作废、退款和不可逆动作

| 场景 | 推荐V1处理 | 审批 |
|---|---|---|
| 未提交、未产生业务影响的草稿 | 创建人可以删除自己的草稿 | 无审批，保留轻量操作日志 |
| 已提交但未支付、未扣权益 | 店长作废，原因必填 | 店长权限 |
| 已支付或已扣会员权益 | 禁止作废和物理删除 | 必须从原单发起退款/冲正 |
| 原路退款 | 从原支付分摊发起 | OWNER批准后执行 |
| 无法原路退款 | 选择替代渠道、填写原因和收款人信息 | OWNER批准；形成异常退款审计 |
| 设施时间修正 | 不覆盖原记录，生成修正记录 | 店长发起、OWNER批准 |
| 支付配置、OWNER角色授权 | 重新认证、影响预览、完整审计 | 由另一个有效OWNER复核；若V1仅一个OWNER，则要求二次认证并生成高风险待办 |

V1不提供任何“直接改余额”“直接改已支付金额”“删除审计日志”或通用SQL入口。

## 9. 服务端授权判定顺序

每个受保护命令按以下顺序判定，任一失败立即拒绝：

```text
有效登录会话
→ 账号与员工状态有效
→ 页面/对象权限
→ 动作权限
→ tenant_id与store_id数据范围
→ 字段权限
→ 当前业务状态
→ 金额/比例阈值
→ 职责分离和审批结果
→ 并发版本与幂等键
→ 执行业务并写审计
```

前端可根据权限返回隐藏或禁用动作，但必须展示可理解原因，例如“该笔改价超过店长10%/50元授权范围，需要老板审批”。服务端拒绝结果包含稳定错误码和请求追踪号，不返回内部策略表达式。

## 10. 权限和审批数据模型要求

至少包含以下逻辑对象：

| 对象 | 核心字段 |
|---|---|
| `role` | tenant_id、code、name、status、version |
| `permission` | resource、action、risk_level |
| `role_permission` | role_id、permission_id、effect、conditions |
| `user_role_assignment` | user_id、role_id、organization/store_scope、valid_from/to、reason |
| `field_permission` | role_id、field_code、view_mode、reveal_allowed、export_allowed |
| `authority_limit` | role_id、business_type、amount_minor、ratio、effective_from/to、version |
| `approval_request` | business_type/id、requested_action、requester、reason、status、policy_version |

高风险授权和阈值变更使用版本化配置；在途审批继续引用创建时的策略版本，不因后续修改而静默改变。

## 11. 验收要点

- [ ] 前台可以正常开始、暂停、继续、换设施和结束服务，但不能改价或支付。
- [ ] 收银员可以按标准价结算，但无法修改价格或审批自己的业务。
- [ ] 店长在同时满足10%和50元限制时可以改价；任何改价均要求原因。
- [ ] 超限改价在OWNER批准前不能进入确认支付。
- [ ] 人工微信/支付宝登记只能显示“待核对”，没有人工“支付成功”按钮。
- [ ] 单笔会员资金扣减达到500元时必须完成验证码校验。
- [ ] 现金差额不超过10元可由未参与该班次交班的店长复核；其他差额由OWNER处理。
- [ ] 已支付单据不能作废或删除，只能从原单发起退款或冲正。
- [ ] 跨门店、越权字段查看、过期临时授权和并发旧版本请求全部被服务端拒绝。
- [ ] 每个高风险动作可以用请求号关联审批、业务结果和审计日志。

## 12. 后续调整规则

本矩阵是 V1 默认基线，不是永久写死规则。营业数据形成后，可由OWNER通过版本化配置调整改价、验证码和差额阈值。每次调整必须提供影响预览、生效时间、操作者和审计记录，不追溯改变历史单据的判定结果。
