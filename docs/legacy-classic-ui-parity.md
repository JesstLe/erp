# 老系统经典 UI 复刻清单

## 1. 文档目的

本文件是经典 UI（`/ui/new/*`）的长期事实来源，用于记录参考系统已经核实的页面结构、按钮、字段、查询条件和业务入口。它不保存账号、密码、验证码、Cookie、顾客明细、手机号、护理记录正文或图片内容。

全量页面的路由覆盖、页面形态和当前完成边界另见 [`classic-page-coverage.md`](classic-page-coverage.md)。页面存在不代表后端已闭环，后端状态必须同时核对缺口矩阵。

完整的机器可读清单位于 [`design-audit/legacy-ui-inventory.json`](../design-audit/legacy-ui-inventory.json)。开发时应先查本文件了解范围，再查 JSON 获取页面级控件和字段证据。

## 2. 遍历方法与安全边界

- 使用已经授权的参考系统会话进行只读浏览。
- 允许打开模块、子页面、查询窗口，以及新增/修改等表单的界面结构。
- 不执行保存、删除、审核、反审核、付款、退款、发短信或其他会改变参考系统数据的操作。
- 本轮按约定排除“股权、微信、云商”三个模块。
- 对 iframe 内动态打开的查询窗口另行采集，避免只记录首页菜单而遗漏筛选条件。

## 4. 已核实的模块入口

### 收银

顾客开卡、储值、预约、护理、签单清账、消费退货、积分增减、兑换礼品、兑换储值、收银交班、退出前台。

房台核心流程已单独复核：空闲房台点击后直接打开最大化消费录单台；顶部顺序为“主单信息、微信预约、会员刷卡、项目列表、产品列表、结算”。项目/产品页均支持分类与“编号/名称/拼音码”查询，卡片展示编号、名称、价格以及服务时长或产品库存。底部顺序为“整单员工、整单顾问、整单折扣、更换房台、合并账单、预结小票、删除账单、返回房台”。经典版实施时将“删除账单”映射为新系统的可审计作废。

现代版 `/facilities` 已复用上述操作台的字段顺序和业务动作，同时保留现代圆角视觉。账单草稿、主单接待信息、整单员工/顾问/折扣、换台、合并、预结、结束服务和收款均连接同一套真实后端；刷新后按接待记录恢复草稿，组合支付、官方支付、会员核验、退款、交班和审计仍由原有权威流程处理。

### 顾客

顾客信息、开卡、储值、预约、护理、消费退货、储值退款、次卡退卡、积分调整、积分兑换，以及顾客消费、储值、项目、产品和门店等统计报表。

顾客模块首页与顾客信息子页已经从通用占位布局替换为旧版专用结构：首页复刻“顾客卡类数量占比 / 本月储值金额走势 / 最新登记顾客列表 / 顾客管理 / 报表查询”；顾客信息页复刻顶部 11 项工具栏、左侧卡类树、17 列宽表格和查询表单。当前真实后端已贯通查询、新增、修改、逻辑停用/恢复、脱敏导出、打印与刷新；缺少聚合、导入、批量修改和按卡类服务端筛选的部分保留原位置并进入缺口矩阵。

### 促销

促销开单、门店促销、现有服务、现有产品，以及促销消费相关报表。

### 进货

进货订单、进货入库、进货退货、进货付款，以及订单、入库、退货、供应商、门店、职员和商品明细报表。

### 销售

销售订单、销售出库、销售退货、销售收款，以及订单、出库、退货、客户、门店、职员和商品明细报表。

### 库存

其他入库、其他出库、库存盘点、商品调价，以及库存状态、库存变化、库存明细和商品/门店维度报表。

### 配货

门店调拨申请、门店退货申请、总部配送出库、门店退货入库，以及申请、配送、退货和商品明细报表。

### 员工

员工信息、业绩考核、奖惩登记、工资计算、工资发放，以及员工服务、储值、售卡、项目、产品和提成明细报表。

工资计算页已核实的流程动作包括：导入工资数据、修改工资项目、计算个人所得税、审核本月工资、反审本月工资、查看科目详情、查询、表格、打印、导出、退出。

### 财务

费用支出、其他收入、银行存取款、跨店结算、业务结算、经营分析、资产负债，以及相关收支和结算报表。

### 报表

包含 26 个直接报表入口。代表性“门店消费统计表”具有查询、刷新、表格、打印、导出、退出工具栏；查询条件包括统计月份、所在地区和所属门店。

### 决策

包含 23 个直接决策分析入口，覆盖门店排名、收入构成、产品分类占比、顾客和商品分析等主题。

### 短信

顾客短信、员工短信、批量短信、已发短信、短信余额、常用短语、短信模板、短信账号和密码管理。

## 5. 通用交互模式

老系统列表与报表页反复使用以下控件：新增、修改、删除、查询、导入、刷新、表格、打印、导出、退出。经典 UI 应保留相同的出现位置和操作顺序，但在后端能力尚未接入时必须显示“待接入”或禁用状态，不能用静态按钮冒充已实现功能。

查询通常以弹窗形式出现；业务单据通常以最大化 iframe 或独立单据窗打开。经典 UI 可以用现代路由和对话框实现，但用户感知顺序应保持一致：模块首页 → 业务入口/报表入口 → 列表 → 查询或调阅单据 → 业务表单。

## 6. 开发顺序

1. 先为 199 个子页面建立可访问的前端位置，并按清单放置工具栏、字段、表头和选项。
2. 将当前 ERP 已有能力映射到经典 UI，继续复用同一套权限、API、租户和门店数据。
3. 对不能映射的功能，在页面上如实标记“后端待接入”，同时登记到后端缺口矩阵。
4. 按核心业务优先级逐项补齐后端，再把前端占位状态改为真实可操作状态。
5. 每个功能必须经过页面加载、权限、字段校验、保存/查询、状态流转、审计和报表回流的端到端验证后，才可标记为完成。

## 7. 当前边界

经典 UI 的页面位置范围已经完成：12 个模块、199 个子页面均具有唯一页面编号、独立可访问路由、参考系统工具栏、查询弹窗、已采集字段/选项、表格结构、打印和 CSV 导出入口。

模块首页不再使用同一张通用仪表盘，而是按参考系统实际结构分为四类：

- 收银：独立前台操作台、设施接待入口和底部业务快捷按钮；
- 顾客、促销、进货、销售、库存、配货、财务、短信：两张模块图表、对应业务列表、右侧管理与查询分组；
- 员工：单张综合业绩图表、员工列表、右侧员工与报表分组；
- 报表、决策：两张顶部分析图、一张底部趋势图，不显示虚构的“最新复单列表”。

图表标题、最新列表标题与字段、右侧分组、入口顺序和“查看更多”折叠行为以老板系统浏览器实际渲染结果为依据。脱敏后的客户端结构参考保存在 [`design-audit/legacy-source-reference/`](../design-audit/legacy-source-reference/)，不包含顾客数据、手机号、凭据、Cookie 或服务器端 PHP 源码。

经典页面统一使用 `/ui/new/legacy/{moduleKey}/{pageId}` 路由。已存在的新系统能力通过“进入已接入业务”连接到真实页面；缺失能力显示“部分接入”或“后端待接入”，危险操作不会伪装成功。

“前端范围完成”不等于 199 个参考页面的后端能力全部完成。页面级后端完成度以 [`legacy-backend-gap-matrix.md`](legacy-backend-gap-matrix.md) 为准，视觉完成度以项目根目录的 `design-qa.md` 为准。
