# 老系统经典 UI 后端缺口矩阵

## 状态定义

- **已接入**：经典 UI 已连接当前 ERP 的真实 API，具备权限与数据隔离。
- **部分接入**：已有相近业务能力，但字段、状态机、报表或老系统操作顺序尚不完整。
- **待接入**：先保留前端位置和交互说明，不能宣称业务可用。
- **不实施**：根据产品决定排除，或因合规风险不进入本期。

| --- | --- | --- | --- |

| 销售 | 部分接入 | 销售订单、出库、退货、收款的完整单据链 | 与服务收银分开建模，允许仅商品销售 |
| 库存 | 部分接入 | 其他出入库、盘点、调价及历史明细不足 | 所有库存变化生成不可覆盖的流水记录 |
| 配货 | 部分接入 | 调拨申请、总部配送、门店收退货状态机不足 | 品牌内门店互通，跨品牌严格隔离 |
| 员工 | 部分接入 | 员工档案、账号权限和品牌自定义岗位已共用新系统接口；工资、奖惩、个税、审核/反审未实现 | 经典“员工信息”不再使用老板系统写死工种；后续补工资期间锁定和计算规则 |
| 财务 | 部分接入 | 银行、跨店结算、资产负债和经营分析不足 | 业务流水与会计口径分层，禁止从报表反写业务单 |
| 报表 | 部分接入 | 旧系统 26 个报表尚未逐一对齐口径、筛选和导出 | 每个指标写清口径、来源表、时间和门店范围 |
| 决策 | 部分接入 | 旧系统 23 个分析页尚未逐一接入 | 只消费已核对的事实数据，不独立制造口径 |
| 短信 | 待接入 | 供应商、模板、余额、发送记录和退订合规 | 未配置供应商前禁用发送；必须保留发送审计 |
| 股权/微信/云商 | 不实施 | 本轮明确排除 | 不生成导航或假功能 |

## 页面级事实来源

页面级控件、字段、选项和表头不在本文件重复抄写，以 [`design-audit/legacy-ui-inventory.json`](../design-audit/legacy-ui-inventory.json) 为准。这样可以避免页面更新后出现两份互相冲突的清单。

## 模块首页数据边界

经典版模块首页的结构已经按老板系统拆分，但不能把经营报表数据冒充成进货、库存、员工或短信数据。当前只有财务、报表和决策首页可以读取现有经营报表接口；其余模块在专项统计接口接入前展示真实空状态和原字段表格结构。

## 经典版隔离与后端适配边界

- 经典版与现代版共用同一租户、门店、顾客、员工、服务档案、资金和审计事实，不建立经典版专属数据库。
- 经典版页面不得直接渲染现代版页面组件。可共用无视觉含义的请求类型、领域服务、权限和数据查询，但经典版路由、工具栏、表格、弹窗和交互状态由 `apps/web/src/classic` 独立实现。
- 经典版操作顺序与现代版差异较大时，在应用层增加经典版适配查询或编排接口；适配层只重排命令和返回经典页面需要的视图模型，不复制领域规则，也不绕过权限、审计和幂等。
- 页面清单 `classicUiManifest.json` 只保存旧系统结构证据，不能作为运行期业务枚举。员工岗位、服务记录分类、卡类、服务项目、产品和门店设施等内容必须从品牌数据字典或业务表读取。
- 已落地的第一批隔离页面为经典版员工信息和顾客服务档案。员工岗位与服务记录分类均为品牌级可配置字典，编码自动生成，名称可修改，不同品牌数据隔离。

后续需要分别补充顾客登记趋势、促销执行、采购金额、销售出库、库存分类与排行、门店配送、员工业绩、短信发送统计接口。每个接口仍须执行品牌隔离、门店范围、角色权限和指标口径校验。

## 缺口关闭条件

每一项从“待接入/部分接入”变成“已接入”前，至少需要：

1. PRD 和状态机已明确；
2. 数据库变更使用可回滚迁移脚本；
3. 接口具备租户、品牌、门店和角色权限校验；
4. 页面字段和按钮与清单一致，且必填/可选规则明确；
5. 正常、异常、撤销和重复提交路径有自动化测试；
6. 关键动作进入审计记录；
7. 报表数据能够从实际业务流水回流并核对；
8. 在测试品牌完成端到端验证。
