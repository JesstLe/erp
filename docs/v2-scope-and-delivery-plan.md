# ERP V2 范围与交付计划

更新日期：2026-08-19

## 完成定义

V2 只有在下列业务链均具备数据库迁移、服务端权限与幂等、可操作前端、自动化测试、真实本地浏览器验收和用户手册后，才可标记完成：

| 顺序 | 业务链 | 当前状态 | 关键验收 |
|---|---|---|---|
| V2-01 | 会员储值与分账 | 已完成首个闭环 | 本金/奖励分账；支付来源；交班汇总；收入不混算 |
| V2-02 | 会员余额消费与验证码 | 已完成本地闭环 | 余额原子扣减；同卡先本金后奖励；达到 500 元核对手机号与 OTP |
| V2-03 | 消费与储值退款/冲正 | 已完成本地闭环 | 从原单发起；累计退款不超原单；最高权限批准；反向流水 |
| V2-04 | 微信/支付宝真实渠道 | 本地代码闭环，待真实商户验收 | Native/订单码、回调验签、查单、幂等、日账单对账、原路退款 |
| V2-05 | 产品销售与库存 | 已完成本地闭环 | 销售快照、出入库流水、并发防超卖、退货反向流水 |
| V2-06 | 审批与字段权限增强 | 已完成本地闭环 | 改价、赠送、退款、敏感字段查看与导出可审计 |
| V2-07 | 更新、备份与 Linux 部署 | Linux仓库闭环，待目标主机演练 | 一键迁移/发布、回滚策略、备份恢复演练、运行监控 |
| V2-08 | 预约与员工排班 | 已完成本地闭环 | 员工/设施冲突；到店转接待；取消/爽约；班次历史 |
| V2-09 | 次卡、积分与储值部分退款 | 已完成本地闭环 | 原单部分退款；赠金按累计比例收回；次卡和积分不可变流水、撤销与过期 |

## 已交付的 V2-01

- 新增兼容式迁移 `V202608180008`，现有消费支付原地回填业务来源，消费单关联继续保留。
- 支付单使用通用业务来源区分消费与会员储值；经营收入只统计消费，交班仍统计全部实际收款。
- 储值本金、奖励金和支付分摊强制平衡；会员账户不能购买自身储值。
- 本金和奖励金分别写入不可变账户流水，数据库使用余额非负、流水唯一和并发令牌保护。
- 现金/人工外部收款要求当前操作员开班；人工外部记录保持待对账。
- 正奖励金仅 `OWNER` 可确认；店长和收银员只能处理无赠送储值。
- 完成表单、账户余额和储值历史回显，并保留本地虚构截图。

## 已交付的 V2-02

- 为本金和奖励金建立带账户类型约束的内部支付方式；每条内部支付分摊必须关联同顾客、同类型的有效会员账户。
- 同一消费单只允许使用一张会员卡的内部资金；只要该卡本金仍有余额，服务端拒绝先扣赠送奖励，需要组合扣款时必须先把本金扣完。
- 任意会员扣款必须核对完整手机号，系统只使用加密查询值比较，不把完整号码写入支付单或审计。
- 会员扣款合计达到 500 元时要求一次性验证码；挑战绑定门店、顾客、消费单和金额，5 分钟有效、最多 5 次尝试、结算后一次性消费。
- 余额校验、借方流水、支付单、消费单结算、验证码消费、幂等结果和审计在同一串行化事务内提交。
- Development 环境提供受控验证码适配器；生产环境不回显，未配置真实短信发送渠道时明确拒绝请求。
- 本地虚构数据完成 700 元本金储值、600 元会员支付，最终余额 100 元；数据库验证贷方/借方流水和 `Used` 挑战状态一致。

## 已交付的 V2-03

- 新增前向迁移 `V202608180010`，支付和消费单增加累计退款投影，原支付、原业务单和原账户流水保持不可变。
- 消费退款按原支付分摊申请，待审批和已完成金额共同占用可退额度；支持部分退款和累计全额退款。
- 会员账户消费退款只回到原扣款账户；现金退款必须归入审批人的当前班次并校验可用现金。
- 会员储值支持从原支付分摊发起部分或全额退款；按累计退款本金比例向上取整收回赠送奖励，余额不足时拒绝，避免赠金套现和拆单舍入套利。
- `OWNER` 批准或拒绝，申请、审批、反向流水、状态投影、审计和幂等结果在同一串行化事务内提交。
- 经营报表增加消费退款和净收入；储值冲正不误减消费收入，交班现金净额包含现金退款和冲正。
- 真实 PostgreSQL 与浏览器完成消费部分退款、储值累计部分退款和全额冲正验收。

## V2-04 当前已交付

- 使用微信支付 APIv3 Native 适配器和支付宝官方 .NET SDK 订单码适配器；私钥、APIv3 密钥和平台公钥均不进入数据库。
- 新增 `V202608180012`，把渠道付款建模为 `Processing + ChannelPending`；确认时间在成功前为空，并由数据库约束渠道、状态、交易号和班次组合。
- 收银台支持整单生成付款码、3 秒轮询查单、手动查单和“先查单后关单”；刷新页面后可从支付处理中消费单恢复付款进度。
- 微信请求/响应 RSA-SHA256、响应时间窗、APIv3 AES-GCM 通知解密和平台密钥标识均校验；支付宝回调使用 RSA2、应用号和金额校验。
- 回调与主动查单共享同一个原子结算入口；重复事件保持幂等，金额或交易号冲突默认失败，关单后迟到成功进入待冲正异常状态。
- 新增 `V202608180013` 和渠道退款状态机；真实渠道消费退款从原分摊发起，审批只进入处理中，微信/支付宝确认成功后才原子冲减本地支付、消费单和退款单。
- 微信使用 APIv3 原路退款与退款查单，支付宝使用官方 SDK 退款与退款查询；重试复用唯一商户退款单号，渠道失败、网络超时或未知状态均不提前完成本地反向流水。
- 收银台显示待审批、渠道处理中、渠道失败和已完成状态；店长可主动查单，只有 `OWNER` 可批准或对明确失败的退款执行安全重试。
- 新增 `V202608180014`、微信/支付宝账单下载适配器、CSV/压缩包解析、SHA-256 存证、自动匹配和五类差异；原始账单不入库。
- 只有 `OWNER` 可执行对账和登记必填处置说明，店长只读；对账与处置均不自动修改原支付、退款、消费单或会员余额。
- 当前只证明本地代码、密码学夹具和 PostgreSQL 状态约束成立；没有真实商户凭据，因此不宣称真实收款已验收。

## 已交付的 V2-05

- 服务和商品可以独立或混合进入消费单；只购买商品或只接受服务都不需要虚构另一类明细。
- 商品消费单确认时预占门店库存，可信结算时才销售出库，未支付作废只释放预占；并发和数据库约束共同防止超卖。
- 商品退货只记录实物回库并新增反向流水，不隐式触发资金退款；资金仍从原支付分摊发起独立审批。
- 产品封面图选填，经过真实文件头、大小、权限和租户范围检查后加密存储，不参与定价与库存。
- 顾客服务档案支持选填文字、图片和消费单关联，不复制金额；档案和附件保留历史事实，不提供覆盖式删除。
- 门店设施配置从日常接待独立，`OWNER` 可跨店维护，店长只维护授权门店；服务说明、设施说明和参考价均选填且绝不自动计费。
- 待录单接待按顾客原名、预计服务、设施和到店时间识别；机器编号降为追溯信息，占用时长自适应显示到秒。
- 服务明细可选择实际服务员工；提成支持成交金额比例或每次固定金额，并在订单行保存员工、规则、基数和金额快照，退款按比例冲减。

## V2-06 当前已交付

- 新增前向迁移 `V202608180020`，建立只增不改的改价策略版本和改价审批实体；历史订单保存策略、金额、阈值、角色及授权人快照。
- 空库初始策略为：店长单行最大优惠10%、整单优惠50元、不能直接提价；整单优惠按优惠行汇总，不允许用提价抵消。
- `OWNER` 可直接授权合法改价；店长超阈值或提价、收银员任意价格偏差都进入待审批。待审批和已驳回订单在服务端禁止确认金额与收款。
- 仅 `OWNER` 可发布策略版本和审批，申请人不得自批；批准只授权订单当前金额快照，不替申请人改写成交价。
- 右上角通知已接真实改价、退款和交班待办，点击可进入对应业务；通知内容不包含完整手机号等敏感字段。
- 顾客姓名保持原名展示；手机号只在界面层隐藏中间四位，输入完整号码仍由服务端 HMAC 查询值精确定位。
- 改价申请、批准、驳回、作废和确认继续使用幂等、并发版本、事务与审计。
- 顾客普通接口继续只返回脱敏手机号；按需查看必须填写目的并留下独立审计，切换顾客或关闭详情后清除页面明文。
- `OWNER` 可导出当前品牌顾客名单，店长只可导出其当前门店建档的顾客名单；姓名保持原名，店长只能导出脱敏手机号，只有 `OWNER` 可主动选择完整手机号。导出目的、范围和条数进入审计，审计不保存手机号明文或文件。
- 单次导出限制为5000条并按查询条件收窄；CSV增加 UTF-8 BOM、引号转义和公式注入防护。侧栏按角色收敛页面入口，所有真实权限仍由服务端角色和门店范围判定。
- 前台顾客详情由服务端剔除会员账户余额，页面也不请求储值记录或服务档案；店长、结算角色和最高权限仍按职责看到所需字段。

## 已交付的 V2-08

- 第25版前向迁移新增预约和员工班次，不改写既有接待、订单、会员或支付历史。
- 预约必须关联当前门店有效顾客和启用服务项目；员工、允许预约的设施均为可选资源。
- 同一员工或设施的待到店预约不可重叠，同一员工有效班次不可重叠；串行化事务处理并发写偏差。
- 到店在同一事务创建接待并复核设施实际占用/清洁状态；预约信息带入接待但不自动生成收费。
- 取消、爽约和班次取消均保留原因与历史；创建和终态转换使用幂等命令，修改使用乐观并发版本。
- 页面支持自动查询、状态筛选、真实分页、新增、修改、到店、取消和爽约；手机号只视觉脱敏，完整号码仍可精确定位。
- 领域测试、真实HTTP/PostgreSQL回归、前端测试、静态检查和生产构建均通过；真实门店排班习惯属于试点校准边界。

## V2-07 当前已交付

- GitHub Actions 在 Ubuntu runner 上执行锁定依赖恢复、后端/前端测试、依赖漏洞检查，并生成带版本、提交、schema 范围和逐文件 SHA-256 的不可变 `linux-x64` 发布包。
- API 同一进程托管 React 静态文件，并提供同时验证数据库连通性和最新关键表的 `/health/ready`；发布槽位只有返回匹配 schema 才可接流量。
- Bash脚本完成 Flyway `validate → migrate → validate`、发布前加密备份、systemd Blue/Green 非活动槽部署、回环及HTTPS双健康门禁和活动版本记录。
- 发布包校验拒绝缺失、多余、重复或越界文件；数据库迁移禁止 baseline、clean、repair 和自动降级。
- 切流后公网健康失败会恢复原代理配置；应用回退从受保护的活动版本记录读取当前 schema，仅允许切回兼容版本，不信任手工输入的 schema。
- 备份使用 `pg_dump` 自定义格式并联合附件、Data Protection 密钥生成内容清单，经 `age` 公钥加密后删除明文；恢复只允许新建名称含 `_restore_` 的隔离数据库并拒绝覆盖。
- 本机已验证 `linux-x64` 发布产物、逐文件清单和包外摘要可生成；开发库曾完成隔离恢复，就绪探针要求schema 30。当前macOS不能运行systemd、Nginx切流和公网IP证书签发，因此不宣称Linux真机链已经验收。

## 已交付的 V2-09

- 第26版迁移为储值单增加已退本金、已收回赠送金与剩余本金投影；退款继续从原支付分摊发起并由 `OWNER` 批准。
- 赠送金按累计退款本金比例向上取整收回，多次退款只收取目标累计值与既有收回值之差；本金或赠送余额已被消费时拒绝退款。
- 第27版迁移新增次卡、只追加次卡流水、积分到期批次和积分使用分摊；数据库禁止修改或删除权益流水。
- 次卡购买次数和赠送次数分账，固定先扣购买次数；核销、撤销和过期均新增流水，关联消费单时校验同顾客与服务项目。
- 积分按最早到期批次优先使用，支持人工增减、人工扣减撤销和显式过期；撤销不能让已过期批次重新生效。
- 页面在顾客详情展示余次、积分批次和历史，提供按角色收口的发放、核销、撤销和过期入口；设施计时不会自动收费或核销权益。

## V2 收口后的外部验收

在目标 Linux 服务器执行一次完整部署、失败切流恢复、应用回退、证书续期、外部告警和加密联合恢复演练；渠道侧等待真实沙箱/商户资料后，再完成两家渠道下单、付款、重复回调、查单、关单、退款、日账单和差错验收。任何人工登记都继续保持“待核对”，不能伪装成渠道确认。

## V2 查询交互增量

- 顾客、员工、服务项目和产品关键词统一为约300毫秒防抖的实时包含词匹配，不再要求点击查询按钮；清空恢复默认列表，状态筛选立即生效。
- 每次查询消费浏览器取消信号，连续输入时旧请求不会覆盖新结果；服务端继续执行100字符上限、角色、租户、门店和限流校验。
- 员工支持姓名、工号、登录账号、岗位及门店名称/编码查询；顾客完整手机号仍只使用HMAC摘要精确定位，不执行明文模糊搜索。
- 第21个前向迁移启用 `pg_trgm` 并建立11个GIN索引；现有库增量执行和21迁移全新空库重建均已通过。
