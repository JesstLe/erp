# 顾客档案与会员账户

适用版本：V2 顾客、会员与敏感字段审计闭环

更新日期：2026-08-18

## 1. 业务边界

顾客档案、会员卡和会员账户是三个独立对象：顾客可以不办会员；一个顾客可以有多张会员卡；每张卡分别建立储值本金、奖励金和积分账户。

V1 完成建档、查询、卡类配置、开卡和零余额账户初始化。V2 已增加独立的[会员储值与资金分账](11-member-topups.md)、[会员余额消费与手机号验证](12-member-balance-payments.md)以及[次卡、积分与储值部分退款](19-service-passes-points-and-partial-topup-refunds.md)；开卡仍不会自动储值，页面也没有“直接改余额”入口。

## 2. 顾客列表与查询

![顾客列表](assets/10-customer-list.png)

列表显示顾客原名；手机号只隐藏中间四位，例如 `138****1234`。查询范围是当前品牌的顾客，不再只限于建档门店；建档门店作为来源字段展示。可以按以下条件查询：

- 姓名：模糊匹配。
- 完整手机号：服务端计算查询摘要，不使用手机号明文检索。
- 手机尾号：输入 4 位数字。
- 会员卡号：完整精确匹配。

在查询框输入后停顿约 300 毫秒，列表会自动加载包含关键词的结果，无需点击查询按钮；继续输入时旧请求会被取消。清空输入框会恢复当前品牌最近的顾客列表。

查询、刷新或打开详情都是只读动作，不会创建会员卡、账户或余额流水。列表使用服务端分页并显示真实总数，每页20条；查询条件改变后自动回到第一页。

普通列表和详情始终只显示脱敏手机号。确因本人核验等业务需要查看完整号码时，点击“按需查看”，填写 2–200 字查看目的后确认。完整号码只在当前详情中临时显示；操作者、顾客、业务目的、服务器时间、请求号和追踪号会写入审计，切换顾客或关闭详情后恢复脱敏。

`OWNER` 和门店店长可以按当前已执行的查询条件导出顾客名单；`OWNER` 的范围是当前品牌，店长只导出当前操作门店建档的顾客。姓名始终按原名导出。店长只能导出中间四位脱敏的手机号，只有 `OWNER` 可以主动勾选完整手机号。每次导出必须填写目的，单次最多 5000 条，并记录是否包含完整手机号和导出条数；CSV 已处理表格公式注入风险。

## 3. 新建顾客档案

![新建顾客](assets/11-customer-create.png)

点击“新建顾客”只会打开表单；点击“确认建档”后才写入。

| 字段 | 是否必填 | 规则 |
|---|---|---|
| 姓名 | 必填 | 1–100 字；列表和详情按原名展示 |
| 手机号 | 必填 | 当前仅支持中国大陆 11 位手机号；保存加密密文、查询摘要和尾号 |
| 性别 | 选填 | 未填写、女、男、其他四个枚举值 |
| 生日 | 选填 | 不得晚于当前日期；详情按原值显示 |
| 来源渠道 | 选填 | 最多 40 字；当前使用业务编码，例如 `WALK_IN` |
| 服务通知授权 | 选填 | 默认未授权；必须依据顾客真实授权勾选 |
| 营销信息授权 | 选填 | 默认未授权；与服务通知分开记录 |

同一手机号已存在有效档案时，系统会阻止再次建档并提示先查询核对。重复点击或网络重试使用同一幂等请求号时，只创建一份档案。

## 4. 编辑、停用与恢复

`OWNER` 和门店店长可以维护顾客基本资料。由于手机号平时只返回脱敏值，编辑前必须先通过“按需查看”填写业务目的并留下审计，再以完整号码打开编辑表单。姓名、手机号、性别、生日、来源、服务通知授权和营销授权均可修改。

保存时服务端检查档案版本和手机号唯一性；其他终端已经修改、手机号属于另一未合并档案时拒绝覆盖。审计只记录非敏感资料前后值，手机号明文、密文和查询摘要都不写入审计。

停用或恢复必须填写2–200字原因。停用不会删除会员卡、账户余额、服务档案、订单或账务流水，只阻止该档案继续参与需要正常顾客状态的新业务；恢复后可以继续使用。已合并档案不得修改或恢复。

只有 `OWNER` 可以合并重复档案。操作人先搜索并选择“最终保留”的正常顾客，系统生成预览，列出源档案会员卡、本金、奖励金、积分、消费单和服务档案数量。以下情况会阻止合并：

- 两个档案不属于同一品牌租户（正常商户会话无法选择到其他品牌的档案）。
- 源档案已经合并，或已经承接过其他合并档案。
- 保留档案不是正常状态。
- 源档案存在进行中/待录单接待、未完成消费单或有效验证码挑战。

确认合并后，源档案记录保留档案编号、操作人、时间和原因并进入 `Merged` 状态。系统采用逻辑归并：历史订单、服务档案、会员卡、账户和不可变账务流水的原始外键不重写，保留档案在读取时聚合这些历史；使用源姓名、完整手机号、尾号或卡号查询时只返回最终保留档案。这样既能统一业务视图，又不破坏历史证据。

## 5. 配置会员卡类


只有 `OWNER` 可以新建并发布卡类。

| 字段 | 是否必填 | 规则 |
|---|---|---|
| 卡类编号 | 系统生成 | 品牌内按 `CT000001` 递增；发布后不可修改、删除后不复用 |
| 卡类名称 | 必填 | 1–80 字 |
| 有效期天数 | 选填 | 1–3650 天；留空表示长期有效 |
| 服务项目折扣 | 必填 | 1折至10折，支持小数，例如9.5折 |
| 产品折扣 | 必填 | 1折至10折，可与服务项目折扣不同 |

卡类创建后立即处于已发布状态。`OWNER` 可以修改卡类名称、有效期和两类折扣；修改只影响后续新建或重新定价的草稿，已确认、已收款的订单继续使用当时的卡类名称、折扣和成交价快照。卡类草稿、版本审批、停用和适用门店规则尚未进入本切片。

## 6. 开通会员


在顾客详情点击“开通会员”，选择已发布卡类后确认。会员卡号可以手工输入，也可以留空由系统根据本次幂等请求号稳定生成。

生效日按当前门店时区计算，不使用浏览器日期，也不直接使用 UTC 日期。到期日按卡类有效期自动计算。一个开卡请求会在同一数据库事务中完成：

1. 创建会员卡。
2. 创建储值本金账户。
3. 创建奖励金账户。
4. 创建积分账户。
5. 写入开卡审计和幂等结果。

任一步失败都会整体回滚，不会留下“有卡但缺账户”的半成品。

## 7. 查看会员卡和账户


会员卡号只显示后四位；本金和奖励金按分显示为人民币，积分按整数单位显示。新账户均为 0。

账户余额字段不是普通可编辑资料。数据库中的会员账户流水禁止更新和删除；未来充值、消费扣款、退款和冲正只能新增业务来源明确的流水，并同步受控余额投影。

会员卡及本金、奖励金、积分和默认通用次卡在同一品牌的各门店可用。卡片的发卡门店、储值单门店和核销门店分别保留，不改变共享余额；不同品牌之间不能查询或使用这些卡和账户。

在设施接待操作台关联会员后，系统会对目录价自动应用卡类的服务折扣或产品折扣。同一顾客有多张有效卡时，各类明细分别选用折扣最优的卡；卡必须已生效、未过期且卡类已发布。会员价与最后使用现金、储值或其他普通支付方式无关，但不能与团购核销叠加。操作人再次手工修改会员价时，系统将其识别为人工改价，必须填写原因并继续执行改价授权或审批。

## 8. 权限与隐私

- 顾客查询和快速建档：`OWNER`、门店店长、前台、收银员。操作必须从授权门店发起，但查询对象是当前品牌顾客；建档记录当前操作门店为来源。
- 开通会员：当前为 `OWNER`、门店店长。
- 卡类配置：当前仅 `OWNER`。
- 会员账户余额和储值记录：`OWNER`、门店店长和收银员；前台只能看到卡类、脱敏卡号、状态与有效期，服务端不会向前台返回账户余额。
- 顾客服务档案：`OWNER`、门店店长；前台和收银员页面不请求也不显示档案内容。
- 完整手机号以应用数据保护密钥加密；查询使用独立密钥派生的 HMAC 摘要。
- 顾客搜索按请求来源限流，降低批量枚举手机号和会员卡号的风险。
- 列表和普通详情接口不返回手机号明文或完整卡号；完整手机号只由单独的目的必填接口短暂返回。
- 完整手机号导出只允许 `OWNER`；门店店长的服务端上限是脱敏导出，不能通过修改前端请求绕过。
- 顾客建档、卡类发布和开卡均记录操作者、请求号、服务器时间和追踪号。
- 完整手机号查看和顾客名单导出也写入只读审计；审计记录保存目的和范围，不保存手机号明文或导出文件内容。

## 9. 待确认与未开放

以下规则尚未得到最终业务确认，因此当前不擅自扩展：

- 家庭成员共用同一手机号时，是否允许多档案以及如何核验。
- 是否提供“更改建档来源门店”这一纯统计字段调整；品牌内重复档案已经允许由 `OWNER` 预览并合并。
- 海外手机号、证件号或其他唯一联系方式。
- 卡类草稿审批、显式限店卡规则和多卡权益合并规则；在限店规则实现前，现有卡默认品牌通用。
- 字段级营销授权时间线。
- 次卡商品定价与正式售卡收款、复杂退卡作价、积分自动发放/兑换和跨店权益清算仍待后续闭环；当前手工权益发放不能冒充已收款交易。
