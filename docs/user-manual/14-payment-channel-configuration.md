# 微信支付与支付宝渠道安全配置

状态：V2-04 下单、付款码、主动查单、关单、验签回调和原路退款代码已形成闭环；尚未使用真实商户凭据验收，渠道账单对账继续开发。

## 1. 当前可以做什么

最高权限账号可在“支付渠道配置”中为当前门店建立微信支付或支付宝的配置映射，并查看服务器凭据是否齐全。页面只保存一个凭据配置名，例如 `PRIMARY_WECHAT`，不接收也不显示以下敏感内容：

- 微信支付 APIv3 密钥、商户私钥；
- 支付宝应用私钥；
- 私钥正文、平台公钥正文或证书正文。

敏感材料只能通过服务器环境变量和访问受控的密钥文件提供。数据库不保存这些值，审计记录也只记录渠道、凭据配置名和启停状态。

## 2. 页面字段

| 字段 | 必填 | 规则 |
|---|---:|---|
| 收银台显示名称 | 是 | 1–80 字，只影响后续收银台展示 |
| 接口环境 | 是 | `Sandbox` 或 `Production`；切换环境不会复制密钥 |
| 服务器凭据配置名 | 是 | 3–40 位大写字母、数字或下划线，且以字母开头 |
| 门店启用 | 是 | 默认停用；启用前服务端重新检查所有必要配置 |

凭据配置名不能填写文件路径、相对路径或私钥内容，从而避免利用页面读取服务器文件。

## 3. 启用前检查

微信支付当前检查应用号、商户号、商户证书序列号、32 字符 APIv3 密钥、商户私钥文件、平台公钥文件、平台公钥标识和 HTTPS 回调地址。支付宝当前检查应用号、应用私钥文件、支付宝公钥文件、HTTPS 回调地址和官方 HTTPS 网关地址。

缺少任何一项时，可以保存“停用”配置用于准备环境，但服务端会以 `PAYMENT_CHANNEL_CREDENTIALS_INCOMPLETE` 拒绝启用。前端开关不是安全边界，直接调用接口也无法绕过。

“服务器凭据结构完整”只代表配置项和文件存在，不代表商户产品权限、证书有效期、网络连通性或真实收款已经验收。只有完成两家渠道的下单、通知验签、主动查单、关单、退款和对账测试后，才允许用于真实营业。

## 4. 收银交易流程

渠道配置启用后，对应的“微信支付 Native”或“支付宝订单码”才会出现在收银台。当前渠道支付必须整单使用一种渠道，不支持与现金、会员余额混合分摊：

1. 收银员先开班，在待支付消费单选择渠道支付并生成付款码。
2. 系统先写入 `Processing + ChannelPending`，此时实收金额仍为 0，消费单保持“支付处理中”。
3. 页面每 3 秒主动查单；渠道异步通知也可以独立到达。两条路径都必须核对签名、商户、商户订单号、渠道交易号和整数分金额。
4. 只有验证结果为成功时，支付单、消费单、接待和渠道事件才在同一数据库事务内完成；重复通知按渠道事件号和摘要幂等处理。
5. “查单并关闭”会先查单。渠道明确未支付并成功关单后，本地支付才取消，消费单恢复待支付，可重新选择支付方式。
6. 网络超时、响应验签失败或状态未知时不会关单、不会结算，也不会生成伪造成功；页面保留进行中状态供继续查询。

关单后仍收到可信的成功结果属于异常竞态，支付单进入 `ReversalRequired` 并保留审计，不会悄悄把已恢复待支付的消费单再次结算。

## 5. 原路退款

只有已经由可信回调或主动查单确认成功的真实渠道消费支付，才允许从原支付分摊申请渠道退款。最高权限审批后，本地退款单先进入“渠道处理中”，不会把渠道受理误写成退款成功：

1. 微信调用 APIv3 原路退款，支付宝调用官方 SDK 退款接口。
2. 每张本地退款单生成唯一且固定的商户退款单号；查询或重试始终复用该号码。
3. 店长和最高权限可查询渠道结果；只有最高权限可对明确失败的退款执行安全重试。
4. 只有渠道可信结果确认金额与退款单一致且状态成功后，系统才在同一事务中冲减支付单、消费单和退款单。
5. 网络超时、验签失败、金额冲突或未知状态都保留本地处理中状态，不会提前影响营业数据。

人工登记微信/支付宝没有可信渠道订单，不能使用原路退款入口。当前渠道退款仅支持一笔渠道分摊，不与现金或会员账户退款混合。

## 6. 数据库与状态记录

前向迁移 `V202608180011` 建立渠道底座，`V202608180012` 增加异步渠道支付，`V202608180013` 增加渠道退款状态和约束：

- `payment_channel_configurations`：门店、渠道、环境和凭据配置名；
- `payment_channel_orders`：外部商户订单号、金额、二维码、渠道交易号及状态；
- `payment_channel_events`：仅保存已验签通知的渠道事件号和 SHA-256 摘要，不保存原始通知正文。
- `payment_channel_refunds`：原渠道订单、固定商户退款单号、渠道退款号、金额、查询时间和处理状态。

渠道订单禁止物理覆盖历史尝试；同一支付分摊同一时间只能有一个活动渠道订单。回调处理以渠道事件号唯一约束实现幂等，通知正文只在当前请求内验签，数据库仅保留 SHA-256 摘要。

## 7. 回调地址与凭据

环境变量中的 `NotifyUrl` 填写对应渠道的回调基地址，例如：

- 微信：`https://erp.example.com/api/integrations/payment-notifications/wechat`
- 支付宝：`https://erp.example.com/api/integrations/payment-notifications/alipay`

系统发起订单时会在末尾追加门店渠道配置 ID。回调接口不依赖浏览器登录，但限制请求体大小和来源速率，并以渠道验签作为信任边界。

## 8. 当前禁止事项

- 不得把真实私钥、APIv3 密钥或证书提交到 Git、数据库或页面表单。
- 不得因为配置项齐全就把人工微信/支付宝登记改成“渠道已确认”。
- 不得在没有真实商户验收证据时，把本地加密测试描述为真实收款已上线。
- 不得通过同步结算接口提交渠道支付方式；服务端会以 `CHANNEL_PAYMENT_REQUIRES_INITIATION` 拒绝。
- 不得用现金退款、人工参考号或渠道“已受理”响应冒充渠道退款成功；只有可信成功结果可以完成本地反向流水。
- 当前尚未开放渠道账单自动对账，不得用手工修改原支付流水掩盖差异。
