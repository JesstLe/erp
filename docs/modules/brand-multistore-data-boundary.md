# 品牌租户与多门店数据边界

更新日期：2026-08-19

## 1. 核心模型

平台采用三级边界：`平台 → 品牌租户（tenant）→ 门店（store）`。

- 一个品牌租户可以有多家门店，同一品牌内共享顾客身份和会员权益。
- 不同品牌对应不同 `tenant_id`，业务数据完全隔离。
- 门店是业务发生地和员工授权范围，不是顾客及会员权益的所有权边界。

## 2. 品牌内共享数据

以下对象按 `tenant_id` 查询和唯一性校验，在品牌内跨店可用：

- 顾客主档、姓名、脱敏手机号、标签、营销授权和合并关系；
- 会员卡、卡类、储值本金、奖励金、积分及其不可变流水；
- 默认通用次卡/权益包；未来如果支持限店卡，必须增加显式适用门店规则，不能复用发卡门店字段；
- 顾客服务档案的品牌内只读视图及图片，仍受服务档案权限控制；
- 品牌级服务项目、产品目录和默认价格规则。

示例：顾客在 A 店建档、开卡并充值 500 元，A 店是建档/发卡/储值发生地。顾客到 B 店后，B 店有权限的员工能够用姓名、完整手机号摘要或卡号定位同一顾客，查看可用余额并完成扣款；扣款流水和消费单记录 B 店。

## 3. 保留门店归属的数据

以下对象必须保存实际门店，默认按员工授权门店读写：

- 设施、服务区、占用计时、预约资源和员工排班；
- 消费单、支付、退款、储值单、次卡核销和积分操作流水；
- 收银班次、渠道配置、渠道订单和对账；
- 库存余额、批次、出入库、盘点和调拨；
- 员工业绩、提成归属、门店收入和经营报表；
- 审计事件与敏感字段查看记录。

这些单据引用品牌级顾客/账户，但不能因为会员跨店共享而丢失业务发生门店。

## 4. 字段语义

| 字段 | 语义 | 是否限制品牌内跨店使用 |
|---|---|---|
| `tenant_id` | 品牌租户和安全隔离边界 | 是，必须相同 |
| `customers.home_store_id` | 首次建档门店 | 否 |
| `membership_cards.store_id` | 发卡门店 | 否 |
| 订单/支付/储值/核销的 `store_id` | 实际业务发生门店 | 是，按操作人门店权限校验 |
| 服务档案 `store_id` | 服务发生/建档门店 | 品牌内可按权限读取，修改规则另行校验 |

为降低数据库变更风险，现阶段不重命名既有 `home_store_id` 和会员卡 `store_id`；通过代码、文档、接口标签和回归测试固定其“来源字段”语义。以后如需改名，按兼容迁移分阶段执行。

## 5. 权限规则

- 员工必须先拥有当前操作门店权限，才能在该店发起接待、预约、开单、储值或扣款。
- 具备顾客读取权限的员工可在其授权门店业务中检索本品牌顾客；手机号仍只做视觉脱敏，完整手机号精确查询使用 HMAC 摘要。
- 会员资金和权益读取、扣减继续要求独立权限、手机号核验、大额验证码、幂等、事务和审计。
- 平台管理员默认只看商户元数据，不直接读取任一品牌的顾客、余额或交易明细。

## 6. 隔离门禁与验收

所有接口和后台任务必须满足：

1. 从已认证身份取得 `tenant_id`，不接受客户端自行指定租户。
2. 所有关联对象都校验相同 `tenant_id`，不能只凭 UUID 查询。
3. 门店操作同时校验当前用户拥有目标门店权限。
4. 数据库唯一键至少包含 `tenant_id`；同一手机号或卡号可以在不同品牌分别存在。
5. 自动化测试覆盖 A 店建档、B 店查询与会员扣款，以及使用另一个 `tenant_id` 查询同一 ID 必须失败。

## 7. 首版默认决策

- 顾客主档、会员卡、储值、奖励金、积分和次卡默认品牌通用。
- 服务档案允许品牌内有权限角色跨店查看，新增记录仍归实际操作门店；历史更正保留原门店和更正审计。
- 库存、现金班次、渠道配置和设施绝不自动跨店共享。
- 跨店消费产生的收入、员工提成与支付归消费门店；会员负债在品牌层汇总，跨店内部核算只在报表/财务规则中计算，不修改顾客余额。
