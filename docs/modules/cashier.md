# 收银模块

## 模块目标

支撑门店前台从识别顾客、选择项目/商品、计算优惠、选择支付方式到生成消费单的完整收银流程。

业务补充后，模块目标扩展为“门店接待 + 设施占用计时 + 服务内容确认 + 收银结算”。详细模型见 [门店接待、设施计时与收银领域设计](../domains/store-service-and-cashier.md)，可执行状态与验收基线见 [V1核心状态机与验收用例](../v1-state-machines-and-acceptance-cases.md)，外部支付开发边界见 [微信支付与支付宝支付开发设计](../payment-integration-development-guide.md)。

## 当前证据

![前台收银房台总览](../assets/cashier/cashier-overview.png)

前台采用房台看板：全部、干净、正在服务、顾客等待四种计数，支持大/小图标、客显和刷新。底部提供顾客开卡、储值、预约、护理、签单清账、消费退货、积分增减、兑换礼品、兑换储值、收银交班等快捷入口。

打开一个空房台后可见主单信息、微信预约、会员刷卡、项目列表、产品列表、结算、项目检索与项目卡片；整单级动作包括员工、顾问、折扣、更换房台、合并账单、预结小票、删除账单和返回房台。

高风险现状：只点击空房台、未选项目且未保存，房台就从“干净”变为“顾客等待”；返回并刷新后仍保留。这证明参考系统把“查看/进入”与“创建账单或占用房台”混在一起。

本轮进一步核对了储值单、消费/储值查询和收银交班，完整证据见 [老板系统：收银与会员资金业务逻辑审阅](../../design-audit/cashier-business-logic-2026-08-18/report.md)。已确认老板系统采用“业务单据 → 多渠道支付分摊 → 单据审核/作废 → 收银交班对账”的资金链；设施状态不直接计算收费。

## 核心业务逻辑

### 核心对象

- 接待记录：表示一次顾客到店，顾客身份可以暂时为空。
- 设施使用记录：记录设施占用、暂停、换台和结束时间，不参与自动计价。
- 消费单：记录本次项目、产品、服务时长、员工、价格、优惠、应收和欠款。
- 支付单及支付分摊：记录现金、外部支付、储值、奖励、签单等实际资金或权益来源。
- 收银班次：汇总收银员当班期间的收入、支出、理论应交、实际交接和差额。

### 主流程

```mermaid
flowchart LR
    A["预约/散客到店"] --> B["创建接待"]
    B --> C["明确开始使用设施"]
    C --> D["服务中/设施计时"]
    D --> E["结束服务并释放设施"]
    E --> F["店长录入项目、时长和实际金额"]
    F --> G["关联会员或散客结算"]
    G --> H["核验价格、优惠和会员权益"]
    H --> I["组合支付/签单欠款"]
    I --> J["生成账户、库存和业绩流水"]
    J --> K["交班对账"]
```

### 状态与关键动作

- 接待：已到店 → 服务中 → 服务已结束/待录单 → 待结算 → 已完成；可取消或标记未消费离店。
- 设施使用：使用中 → 暂停/继续 → 已结束或已取消；设施看板的可用、使用中、暂停、待清洁状态由基础状态和有效记录推导。结束设施使用不等于完成支付。
- 消费单：草稿 → 待确认 → 待支付 → 支付处理中 → 已结算；异常状态包含已作废、部分退款、已退款和待冲正处置。
- 支付结果、单个支付分摊的确认状态和财务对账是三个独立状态轴；人工登记待核对、渠道确认和财务已匹配不得混写。精确定义以状态机文档为准。
- 收银班次：未开班 → 当班中 → 待交班 → 待复核 → 已关班；存在差额时不得静默关班。

### 关键规则

- 设施占用、服务内容和消费结算是三个独立业务动作；查看设施不得产生任何业务写入。
- 服务和商品互不强制绑定；消费单可以仅服务、仅商品或混合，至少有一条明细即可。服务行不要求商品，商品行不要求服务时长。
- 同一设施同一时刻只能服务一张接待单；一张接待单可以关联多个不同设施，每段设施使用独立计时，结束后支持待清洁状态。
- 标准价格由最高权限账号维护并版本化；店长只在授权范围内确认实际成交价，差异必须记录原因。
- 会员可按姓名和手机号辅助查找；扣减储值、奖励、次卡或积分前核对完整手机号，大额扣减按配置要求验证码。
- 结算必须满足：支付分摊合计 = 实收金额，实收金额 + 新增欠款 = 应收金额。
- 储值、奖励、次卡和积分使用系统内部账户核验；同卡消费固定先扣储值本金、本金耗尽后才可扣奖励，余额不足或并发版本冲突时禁止扣减。
- 产品明细只有在消费结算成功或明确的出库动作后才产生库存流水；服务项目不动库存。
- 已结算单据不能物理删除；只能按原单发起退款、冲正或红字处理。
- 支付、会员权益、库存、员工业绩任一环节失败时，整笔结算必须返回可恢复状态，不能显示整体成功。

### 跨模块关系

- 从顾客模块读取会员身份、卡类、储值、次卡、积分和欠款。
- 从促销与商品主数据读取适用价格、优惠和项目/产品档案。
- 向库存模块发送产品出库或退货入库事件。
- 向员工模块发送服务、销售、顾问和分成归属事件。
- 向财务模块发送收款、退款、签单应收、手续费和交班差额。
- 向报表/决策模块提供客流、项目、产品、支付、退款、设施利用率和班次数据。

## 需求拆解草案

- 需求：支持散客与会员两种结算方式；服务开始时可暂不识别顾客，结算前再完成关联。
- 需求：消费单支持项目、产品、次卡核销、储值/奖励扣款、优惠券及组合支付。
- 需求：消费单明细支持仅服务、仅商品和服务商品混合三种组合，不得以缺少另一类型为由阻止保存或确认。
- 需求：结算前预览金额构成，付款动作与保存草稿分离。
- 需求：撤销、退款、反结算等高风险动作单独授权并全量记录。
- 需求：查看房台不得写入；必须通过“开始接待/创建主单”显式占台，并显示创建人、时间和自动释放规则。
- 需求：设施占用记录与消费单独立建模。开始使用后计时，结束服务后停止计时并释放设施，账单可以稍后结算。
- 需求：区分项目标准时长、设施实际使用时长和项目实际服务时长；不采用“计费时长”。设施计时只记录运营信息，与收费无自动关系；最终收费金额由店长根据服务内容输入或确认。
- 需求：开始使用设施时允许暂不识别顾客；服务结束后可通过姓名、手机号或会员卡关联会员，再读取储值、次卡、积分和会员价。
- 需求：开始使用设施时可选关联当前门店顾客和预计服务项目；两者仅用于在设施看板和待录单队列中识别本次接待，不形成收费承诺。顾客名称按权限脱敏，手机号不进入设施看板。
- 需求：待录单队列以“顾客简称 + 预计服务 + 经历设施 + 到店时间”为主标题，机器生成的接待单号降为次要追溯信息；匿名接待也必须通过设施、时间和备注提供足够上下文。
- 需求：待录单占用时长按时、分、秒自适应展示，避免多个不足一分钟的接待都显示为零分钟；秒数只用于记录与识别，不改变独立计价规则。
- 需求：选择待录接待后自动恢复已关联顾客；预计服务只有在操作人明确点击“带入预计服务”后才成为可编辑草稿明细，且仍需保存草稿、确认金额和收款三个显式动作。
- 需求：计时以服务端为权威，页面刷新、换电脑或断线重连后仍连续准确。
- 需求：换设施必须保留前后两段使用记录；人工改时长需要权限、原因和审计。
- 需求：接待负责表达已到店、服务中、服务结束、待结算和已完成；消费单负责表达草稿、待确认、待支付、支付处理中和已结算；设施看板状态由设施基础状态、有效使用记录和清洁任务推导，三者不得共用一个状态字段。
- 需求：项目/产品加入、员工/顾问归属、折扣、合并账单、预结和结算都需要清晰的金额变化反馈。
- 需求：结算前展示原价、优惠、储值/次卡抵扣、欠款、应收、实收、找零和支付组合；提交支付与打印小票分离。
- 需求：项目、产品、卡类和会员价由最高权限账号维护并版本化；店长只在授权范围内确认实际成交价，价格差异、原因和操作者必须留痕。
- 需求：支付方式采用配置表与支付分摊明细，不在消费单上为现金、微信、支付宝等建立固定金额列。
- 需求：微信 Native 与支付宝订单码通过统一支付中心接入，不能在消费单上写渠道专属逻辑；接口未通过验收、未启用或不可用时只能“人工登记待核对”，交班/财务核对后才变为“已核对”。
- 需求：储值本金、奖励金、次卡和积分使用独立会员账户及不可变流水；同卡先本金后奖励，内部余额不足时禁止结算。
- 需求：交班按门店、收银员、班次、业务类型和支付方式计算理论金额，录入实际交接金额并追踪差额。
- 需求：删除账单改为“作废”，要求原因、权限与日志；已发生支付或服务的账单不得直接删除。
