# 角色权限闭环（PRD 与实现基线）

更新日期：2026-08-19  
状态：V1 已实现并通过自动化回归

## 1. 目标与边界

系统使用“员工可兼任多个角色、权限取并集、门店范围另行约束”的 RBAC 模型。隐藏菜单只用于减少干扰，不作为安全边界；任何受保护操作都必须由服务端读取数据库授权记录并再次判定。

V1 允许最高权限账号给员工分配预置角色，不开放任意新建权限码、任意 SQL 或绕过审计的超级入口。角色默认授权记录保存在 `authorization_role_permissions`，后续撤销某项授权后，下一次页面刷新和下一次 API 请求都必须立即按新授权执行。

## 3. 页面内动作规则

- 目录和价格对所有岗位提供工作所需的只读信息；只有具备 `catalog.write` 或 `price.publish` 的账号显示新增、编辑、停用、删除、草稿、发布和取消按钮。
- 前台可建顾客、操作设施和预约，但不能进入收银、扣会员资金、退款或改价审批。
- 收银员可建顾客、查看结算所需会员权益、储值、录单和收银，但不能进入库存、经营报表或设施操作。
- 店长可处理授权门店经营、库存查看、盘点发起/取消、交班复核和报表；不能维护全局目录价格、员工角色、支付密钥或高风险审批。
- 最高权限账号可维护目录、价格、组织、员工、支付渠道、库存过账和高风险审批，但仍受状态机、原因、并发版本、职责分离和审计约束。
- 技师当前只能查看工作台和已启用目录/价格；“本人任务”专页仍属于后续独立模块，不能用扩大其他页面权限替代。

## 4. 强制执行链

每次请求按以下顺序处理：

```text
有效登录与首次改密检查
→ 数据库角色授权记录
→ 页面/动作权限码
→ tenant_id 与 store_id 范围
→ 字段和敏感信息级别
→ 业务状态、金额阈值与职责分离
→ 并发版本和幂等键
→ 执行业务并写审计
```

前端包含三层体验控制：左侧菜单过滤、路由拦截、页面按钮过滤。手工输入未授权网址会进入统一 403 页面。服务端使用命名权限策略查询 `identity_user_roles → identity_roles → authorization_role_permissions`；篡改浏览器权限数据不能绕过 API。

工作台按权限请求数据：没有 `report.read` 的岗位不会请求经营金额接口，也不会把无权限误显示为零；快速入口只显示当前可访问模块。

## 5. 数据库与版本更新

迁移 `V202608190030__role_permission_catalog.sql` 只追加缺失的默认授权，使用唯一约束避免重复，不修改历史角色、员工、业务流水或审计记录。新商户初始化、平台审核建商户和开发种子初始化都使用同一权限目录生成授权记录。

未来调整默认权限必须同时完成：

1. 新增前向迁移，明确新增或撤销哪些角色授权；禁止直接修改已执行迁移。
2. 更新权限目录、页面映射和角色矩阵文档。
3. 增加“有权限成功、无权限 403、跨门店 403、兼职角色并集”回归。
4. 先在测试环境升级、备份和验证，再执行生产 Blue/Green 发布。

## 6. 验收标准

- 未登录返回 401；已登录但权限不足返回 403。
- 隐藏页面不能通过手工 URL 或直接调用 API 绕过。
- 前台不能收银；收银员不能读库存；技师不能读顾客、金额、报表和审计。
- 店长只能操作授权门店；切换门店不能扩大数据范围。
- 多角色权限取并集；未知角色不获得任何业务页面权限。
- 撤销数据库授权后，不依赖重新编译前端即可阻止对应服务端接口。
- 完整手机号、支付配置、价格发布、退款批准等敏感动作继续执行专项权限与审计规则。
