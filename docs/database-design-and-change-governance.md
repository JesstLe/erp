# 数据库设计与变更治理规范 v1

日期：2026-08-18  
适用范围：ERP 开发、测试、发布、生产运维和数据修复。  
当前测试基础设施：Windows 云服务器，2核 CPU、4GB 内存、70GB 磁盘；正式生产操作系统另行评审。

## 1. 目标与底线

业务变化必然会带来数据库变化。本规范的目标不是禁止改表，而是保证每次变更都可识别、可验证、向后兼容、可恢复和可审计。

生产数据库底线：

- 禁止开发人员使用图形工具或SQL客户端直接手工改生产表。
- 禁止ORM在生产环境使用自动同步、自动建表或自动删除字段。
- 禁止应用启动时自动执行生产迁移。
- 禁止修改已经在任何永久环境执行过的迁移文件。
- 禁止在同一次发布中直接删除旧字段并要求新程序立即使用新字段。
- 禁止物理删除已生效的资金、库存、会员权益、工资和审计记录。
- 禁止生产应用账号拥有建表、改表、删表或创建高权限账号的权限。

## 2. 技术基线

### 2.1 数据库

第一版采用 **PostgreSQL 18**，并持续升级该主版本当前安全修复版本：

- 支持事务、外键、唯一约束、检查约束、JSONB、行级锁和丰富索引。
- 适合消费、库存、会员余额、应收应付等强一致性业务。
- 官方提供Windows安装包，适合当前服务器环境。
- 支持逻辑备份、基础备份、WAL归档和时间点恢复。

PostgreSQL 18 在当前 Windows 测试环境完成兼容、备份和恢复验证后写入部署清单；应用上线后不自动跨大版本升级。未来生产环境即使改用 Linux 或托管数据库，也保持相同主版本和迁移历史。

### 2.2 数据库迁移

第一版默认采用 **Flyway CLI + 版本化SQL迁移**：

- 迁移文件与应用代码一起进入版本控制。
- Flyway使用 `flyway_schema_history` 记录版本、校验值、执行时间和结果。
- 发布前执行 `validate`；校验失败时禁止继续发布。
- 已执行的版本化迁移不可修改；修复必须增加新迁移并向前演进。
- 生产环境禁止执行 `clean`；`repair` 只允许在事故评审后由数据库负责人执行。

迁移目录约定：

```text
db/
  migrations/
    V202608180001__baseline_core_schemas.sql
    V202608180002__create_customer_and_member_tables.sql
    V202608180003__create_cashier_and_payment_tables.sql
  repeatable/
    R__reporting_views.sql
  checks/
    pre_release_checks.sql
    post_release_checks.sql
```

版本采用 `VyyyyMMddNNNN__description.sql`，避免多人开发时版本冲突。文件名、说明和SQL内容使用英文，业务注释可以使用中文。

### 2.3 数据库账号

至少分离以下账号：

| 账号 | 权限 | 使用场景 |
|---|---|---|
| `erp_app` | 业务表必要的SELECT/INSERT/UPDATE和受控函数执行 | 正式应用运行 |
| `erp_migrator` | 指定schema内DDL和迁移记录 | 受控发布窗口 |
| `erp_readonly` | 脱敏视图和授权报表只读 | 报表、排障 |
| `erp_backup` | 备份所需只读及必要复制权限 | 自动备份 |
| 管理员账号 | 集群管理 | 仅应急和受控运维 |

账号密钥不得写入代码库、迁移文件或普通日志；生产密钥与开发/测试完全不同。

## 3. 环境隔离

| 环境 | 数据 | 用途 | 变更方式 |
|---|---|---|---|
| 开发 `dev` | 合成数据 | 日常开发和迁移试错 | 开发者迁移 |
| 测试 `test` | 合成或脱敏数据 | 集成测试、升级与恢复演练 | 发布候选迁移 |
| 生产 `prod` | 正式业务数据 | 门店正式使用 | 受控发布流程 |

规则：

- 三个环境使用独立数据库、账号、密钥、附件目录和外部服务配置。
- 生产数据不得直接复制到开发环境；确需复现问题时生成最小脱敏数据集。
- 当前2核4G服务器只承载测试环境，不与未来生产数据库混用。
- 开发环境运行在开发电脑；测试服务器接收CI发布包、合成数据和受控验收任务。
- 正式生产环境建立时必须使用独立数据库、账号、密钥、备份和恢复链路，不能把当前测试库原地改名为生产库。

## 4. 数据表设计原则

### 4.1 统一字段

业务表根据需要统一包含：

- `id`：全系统采用应用生成的UUIDv7；业务可见单号使用独立编号规则，禁止拿主键充当业务单号。
- `tenant_id`：租户范围；即使第一期单品牌，也为未来隔离保留。
- `store_id` / `organization_id`：存在门店或组织归属时必须明确保存。
- `created_at`、`created_by`、`updated_at`、`updated_by`。
- `version`：需要并发编辑的对象使用乐观锁版本号。
- `status`：使用明确受约束的状态码，不用自由文本。

时间统一按UTC保存，界面按门店时区展示。人民币收付和账单合计使用以“分”为单位的 `bigint`；单价、成本、数量和比例根据业务精度使用受限 `numeric`，计算后按明确舍入规则落成分；禁止使用浮点数保存金额。

### 4.2 主数据与历史版本

- 顾客、员工、门店、项目和产品使用稳定内部ID，编码和名称可以变化但不替代ID。
- 已被业务引用的主数据不物理删除，只能停用。
- 项目价格、促销、提成、会员权益和审批规则使用版本表及生效区间。
- 历史单据保存当时使用的版本ID和必要快照，不能使用当前价格重算历史。

### 4.3 台账与余额

会员储值、奖励、积分、次卡、库存、应收应付、支付、退款和员工业绩采用“不可变流水 + 受控余额快照”：

- 流水只追加，不覆盖原记录。
- 错误通过冲正流水或补偿流水修复。
- 每条流水保存业务类型、业务单号、业务明细、方向、金额/数量、发生前后余额和幂等号。
- 余额快照用于快速查询，但必须能够通过流水重新计算和校验。
- 同一账户或库存维度更新时使用事务、行锁或乐观锁，防止并发超扣。

### 4.4 可扩展设计

- 支付方式使用 `payment_method` 配置和 `payment_allocation` 明细；新增支付渠道不新增消费单字段。
- 价格使用价格簿和价格版本；新增门店价或会员价不复制整张商品表。
- 单据与上下游通过明确来源关系表关联，不把所有来源塞进一个无约束字符串。
- 非核心可变信息可以进入受控扩展字段；金额、状态、权限、余额和业务主关系不得只保存在JSON中。
- 不使用EAV模型承载全部核心业务，避免校验、索引、报表和外键失效。
- 功能上线使用功能开关控制，但数据库结构必须先向后兼容。

### 4.5 约束优先

以下规则同时在应用层和数据库层实现：

- 租户范围内业务编码唯一。
- 同一设施同一时刻只有一条有效使用记录。
- 支付分摊金额不得为负，合计必须通过结算服务校验。
- 会员账户和库存不得因并发操作出现未授权负数。
- 外键保证单据、明细、账户和来源关系存在。
- 检查约束保证金额、数量、比例和时间区间合法。

数据库约束失败必须转换为可理解的业务错误，不能向用户显示原始SQL或堆栈。

## 5. 迁移分级

| 等级 | 示例 | 发布要求 |
|---|---|---|
| M1 加法兼容 | 新表、可空字段、新索引、配置值 | 自动验证后进入发布窗口 |
| M2 数据迁移 | 历史回填、拆分字段、重算快照 | 测试库全量演练、批次执行、对账 |
| M3 破坏性变更 | 删除字段、改类型、合并表、改变唯一键 | 至少跨两个正式版本执行，专项审批 |
| M4 高风险账务修复 | 余额、库存、支付、应收应付修复 | 双人复核、备份、逐笔结果和审计 |

M2以上迁移必须在变更单中写明：影响表、预计行数、预计耗时、锁风险、磁盘增长、兼容程序版本、检查SQL、恢复方式和责任人。

## 6. 扩展—迁移—收缩

所有破坏性调整采用以下流程：

```mermaid
flowchart LR
    A["扩展：增加新结构，保留旧结构"] --> B["部署兼容新旧结构的程序"]
    B --> C["双写/受控回填历史数据"]
    C --> D["核对数量、金额、余额和失败记录"]
    D --> E["切换读取新结构"]
    E --> F["观察至少一个正式版本"]
    F --> G["停止旧写入"]
    G --> H["独立版本收缩旧结构"]
```

示例：把 `service_order.wechat_amount` 改造成可配置支付明细时：

1. 新增 `payment`、`payment_allocation` 和 `payment_method`，旧字段保留。
2. 新程序写支付明细，并在过渡期保持旧字段兼容。
3. 分批将历史支付列回填为支付明细，记录进度和异常单据。
4. 对账确认新旧金额一致后切换读取。
5. 至少经过一个稳定正式版本后停止旧字段写入。
6. 再经过独立审批版本才删除旧字段。

## 7. 大表与在线变更

- 新字段优先允许为空或提供兼容默认值，历史数据分批回填后再收紧约束。
- 大批量回填使用小批次、检查点、限速和可重入任务，不能一个事务锁住整表。
- 创建大索引使用数据库支持的低锁方式；PostgreSQL可评估 `CREATE INDEX CONCURRENTLY`，并单独处理其事务限制。
- 修改类型、重建索引、验证约束前在测试库用接近生产的数据量测量耗时和额外磁盘。
- 迁移期间监控锁等待、连接数、CPU、内存、磁盘、WAL增长和错误率。
- 超过发布窗口或预设阈值立即停止后续步骤，不强行完成。

## 8. 迁移与数据修复分离

- 结构迁移负责表、列、约束、索引和少量确定性参考数据。
- 大规模历史回填使用可恢复的数据迁移任务，不塞入应用启动过程。
- 账务数据修复使用单独编号的修复单和脚本，先生成影响预览，再执行。
- 每个修复记录原值、目标值、原因、业务单号、审批人、执行人、执行时间和结果。
- 修复脚本默认只允许处理明确ID清单，禁止无条件全表UPDATE或DELETE。

## 9. 发布门禁

生产迁移必须依次完成：

1. 迁移文件代码审查和安全审查。
2. 从空库执行全部迁移成功。
3. 从当前生产版本的测试备份升级成功。
4. Flyway `validate` 成功且无缺失、未来或校验值冲突。
5. 自动测试、关键流程冒烟和数据不变量检查成功。
6. 确认生产磁盘空间、当前schema版本、长事务、锁等待和未完成任务。
7. 生成发布前备份并取得备份编号。
8. 在批准的低峰窗口由 `erp_migrator` 执行。
9. 执行发布后检查并观察错误、锁、性能和关键金额。
10. 记录应用版本、数据库版本、备份编号、执行人和结果。

禁止应用进程自行决定何时升级生产数据库；迁移是独立发布步骤。

## 10. 恢复与回退

必须区分：

- **程序回退**：重新部署上一程序版本；依赖数据库保持向后兼容。
- **迁移撤销**：只用于已经验证为完全可逆、且没有新业务数据写入的迁移。
- **补偿迁移**：生产已写入新结构后，优先通过新迁移向前修复。
- **备份恢复**：用于严重数据损坏；先恢复到隔离数据库核对，再决定切换或提取修复数据。

不能把“存在down脚本”当作恢复保证。删除字段、合并数据、重算金额等通常无法通过简单反向SQL可靠恢复。

## 11. 备份与恢复目标

第一版目标：

- RPO（可接受数据丢失）：不超过15分钟。
- RTO（恢复服务时间）：不超过4小时。
- 每日一次自定义格式逻辑备份，便于对象级恢复和跨版本迁移。
- 每周一次基础备份，并连续归档WAL以支持时间点恢复。
- WAL归档或等效备份代理必须保证已提交变更在15分钟目标内安全传出本机；配置归档切换周期前先测算额外WAL存储，并持续监控 `pg_wal` 积压。
- 每次生产发布和M2以上迁移前创建独立备份或云盘快照。
- 备份至少保留7个日备份、4个周备份和3个月度备份。
- 至少一份备份位于当前云服务器和当前系统盘之外。
- 每月执行一次抽样恢复，每季度执行一次完整恢复演练。

备份成功以“能够恢复并通过校验”为准，而不是以“文件生成成功”为准。

## 12. 安全要求

- 所有SQL使用参数化查询，禁止拼接外部输入。
- 每个接口在服务端校验租户、门店、角色、动作和字段权限。
- 手机号、证件、薪资、银行账户和密钥按敏感等级存储、脱敏和审计。
- 数据库端口不向公网开放；只允许本机应用或受控管理网络连接。
- 备份文件加密并限制访问，下载和恢复行为记录日志。
- 应用错误不暴露SQL、表结构、连接字符串或堆栈。
- 生产只启用必要扩展；安装和升级数据库扩展进入同一变更流程。

## 13. 负责人和审批

正式开发后明确以下职责：

- 数据库设计负责人：审查模型、约束和迁移策略。
- 发布负责人：执行迁移与应用发布，不负责业务审批。
- 业务负责人：确认价格、余额、库存和财务口径。
- 复核人：复核M3/M4变更、备份编号和执行结果。

即使早期由同一团队成员承担多个角色，生产发布记录中仍要明确“提出、审查、执行、复核”四个动作。

## 14. 实施阶段门禁

在开始编写核心业务代码前，必须先完成：

- PostgreSQL版本与Windows Server版本兼容确认。
- Flyway最小迁移项目和空库重建测试。
- `dev/test/prod`连接配置与账号隔离。
- 一次逻辑备份、基础备份、WAL归档和隔离恢复演练。
- 核心台账并发扣减原型测试。
- 一次“增加字段—回填—切换—程序回退”演练。

以上门禁未完成时，可以开发页面原型，但不得接入真实顾客资金或正式库存。
