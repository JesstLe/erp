## 你要实现的需求拆解
- **商品库存逻辑**
  - 收银中商品列表要显示当前库存
  - 选中商品加入收银单时 **暂不扣库存**
  - 只有收银结算成功后，才真正扣减库存
- **服务员/技师提成**
  - 给单个产品/服务项指定“销售员/技师”
  - 每条明细按提成比例或固定金额计算提成
  - 提成规则可以配置（已有 CommissionRule，可复用）
- **服务时长与倒计时**
  - 现在逻辑：服务完成后再收银结算
  - 想要逻辑：在收银页面点击服务/产品后，先进入“服务时长过程”：
    - 创建一个“服务进程/计时任务”，开始倒计时（可自定义时长）
    - 倒计时最后 3 分钟有语音提醒
    - 切换/关闭再打开设备（座位）不会清空已选内容，仍然显示剩余时间
    - 倒计时结束后，才允许/引导去结算，结算完才真正“清台”

## 功能设计思路（不改动原有“出库/提成”核心结构）

### 一、商品库存：显示 + 结算扣减
1. **商品列表显示库存**
   - 后端：直接复用已有 `/material/list`，但前端调用时要带上当前门店/仓库 `depotId`（从当前会话 `CashierSession.depotId` 或门店列表里带过去），确保 `stock` 是“本门店库存”。
   - 前端 UI：在 `CashierDeskModal.vue` 的商品卡片上，加一行显示 `库存：item.stock`，并根据 0/不足给出颜色提示（例如灰色/红色）。

2. **结算时统一扣库存**
   - 仍然保持“购物车只是记录数量，不改库存”的模式。
   - 在 `CashierSettlementService.checkout()` 最后、clearSeat 之前：
     - 根据 `sessionId` 查询会话中所有产品明细（`cashierCartService.listProductsBySessionId`），构造一张“销售出库单”的 `DepotHead + rows` 数据：
       - `DepotHead.type = 出库`，`subType = 销售`，`number` 用新的单号;
       - 明细行里填：`materialId`/`barCode`、`operNumber=qty`、`depotId=session.depotId`、必要时 `batchNumber`/`snList`；
     - 调用现有 `depotHeadService.addDepotHeadAndDetail(head, rows, request)`：
       - 自动校验库存（是否允许负库存按系统参数）
       - 自动刷新 `MaterialCurrentStock` 实时库存
   - 失败回滚：`checkout()` 已经是事务方法，若库存不足抛异常，整个结算会 rollback，前端会收到错误提示（如“库存不足”）。

### 二、销售员/技师提成（与服务/产品绑定）
1. **数据建模**
   - 服务提成：
     - 已有 `ServiceOrder` 中的 `technicianId` 字段和 `CommissionRule` 规则，当前 `finishOrder()` 会按规则计算 `ServiceOrderItem.commissionAmount`。
   - 产品提成：
     - 可以扩展 `CashierSessionProductItem` 增加字段：`salesUserId`、`commissionAmount`；
     - 或者新增一张专门的提成明细表，如 `cashier_commission_item`，关联 `sessionId + itemId`，记录提成人、规则与金额。

2. **前端交互**
   - 在 `CashierDeskModal.vue` 的“已选服务/产品明细”行上增加“选择销售员/技师”的控件：
     - 可复用已有员工列表接口 `/person/list` 或 `/user/list`；
     - 每行存一个 `salesUserId`（产品）或 `technicianId`（服务）。

3. **提成计算**
   - 服务：继续使用 `ServiceOrderService.finishOrder()` 里的 `calcCommissionAmount`，规则由 `CommissionRule` 表配置（已经支持按项目、按技师、按技师全场三种维度，按比例或固定金额）。
   - 产品：新增一个类似的 `calcCommissionAmountForProduct`：
     - 规则表可复用 `CommissionRule`，增加 `PRODUCT` 相关的 `ruleScope`，如 `PRODUCT_ITEM/SALESMAN_ITEM/SALESMAN_ALL`；
     - 结算成功后，按每条产品行的金额和销售员算一条提成记录。

### 三、服务时长与倒计时流程
1. **状态建模**
   - 对现有 `CashierSession` 增加“服务时长状态”：
     - 可以新增字段：`status` 细分（例如 `OPEN` → `IN_SERVICE` → `READY_TO_CHECKOUT`）；
     - 或新增一张 `ServiceTimer` 表：字段包括 `sessionId`、`serviceItemId`、`startTime`、`durationSeconds`、`status`（RUNNING/PAUSED/FINISHED）、`remainSeconds` 等。

2. **前端倒计时逻辑（关键是“台位切换不丢状态”）**
   - 在前端只做“展示和本地计时”，真实状态以服务端为准：
     - 收银页面选中服务时，调用后端 `/cashier/serviceTimer/start` 创建/更新计时记录，返回 `endTime` 或 `remainSeconds`。
     - 前端本地用 `endTime - now()` 做倒计时显示；
     - 关闭/打开设备时，重新调用 `/cashier/serviceTimer/currentBySession`，拿到最新剩余时间，继续倒计时，这样不会因为刷新页面就丢状态。
   - 自定义时长：在“添加服务”时让收银员输入或选择服务时长，作为 `durationSeconds` 传给后端。
   - 最后三分钟语音提醒：
     - 前端倒计时组件在 `remainSeconds <= 180` 且尚未提醒时，播放一次本地音频（HTML5 audio）。

3. **与“结算清台”联动**
   - 在结算按钮 `handleCheckout()` 里增加校验：
     - 调用 `/cashier/serviceTimer/checkStatus`，如果还有 RUNNING 状态的计时，要求先“结束服务”或确认提前结算；
     - 正常流程下，倒计时结束后，后端将计时状态设为 `FINISHED`，前端 UI 显示“可结算”。
   - 仍然由 `CashierSettlementService.checkout()` 决定是否 `clearSeat`：
     - 倒计时结束 + 结算成功 → `clearSeat=true` 清台；
     - 如果客户暂时不结算（例如续时），则只停表不清台。

### 四、设备切换/关闭不清空已选内容
- 目前“已选服务/商品”和会话状态是持久化到数据库里的：
  - 服务在 `jsh_service_order`、`jsh_service_order_item`；
  - 产品在 `jsh_cashier_session_product_item`；
  - 会话在 `jsh_cashier_session`，台位在 `jsh_seat`。
- 所以：
  - 只要不关会话（不调用 `closeSession`），切换设备/刷新页后，前端用 `/cashier/session/currentBySeat` + `/cashier/session/detail` 就能恢复“已选内容”。
  - 倒计时状态交给后端的 `ServiceTimer` 记录，就可以实现“关/开设备不清空，并且仍然知道剩余时间”。

---

整体上，你要的三大需求（库存、提成、服务时长）都可以在现有架构上自然扩展：
- 库存：复用 `DepotHead/DepotItem` 的出库逻辑，把出库动作挂在收银结算上。
- 提成：服务提成已有实现，产品提成可以沿用同一套 `CommissionRule` 设计。
- 时长/倒计时：新增一套“服务计时”模型，让会话 + 服务订单之间多一层“计时任务”，前端只负责展示和提醒。
